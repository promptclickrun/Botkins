# Botkins

Botkins is a desktop app for macOS and Windows where you keep a team of AI bots. The bots run on the model plans you already have: GitHub Copilot, ChatGPT, Claude, OpenCode and others. The phone app with the same name pairs with it.

Open **Home** to chat with your bots. **Today** holds panels they publish and maintain. **Chats** keeps conversations, and **Work** holds routines, projects and tasks, with **Activity** for every request and scheduled refresh and a link to its chat. **Wiki** is the shared notebook that you and your bots keep about goals, projects and people.

## Using Botkins

To run Botkins on a server with no screen, install the terminal host: one command installs it as a service, and you operate it with `botkins` from a terminal. See [Run Botkins from a terminal](docs/terminal.md). If a paired phone must view or control a display on the server, use the [Docker setup with a virtual display](desktop/README.md).

Open **Settings → Marketplace → Plugins** to search GitHub’s plugin catalogs or add your own marketplace. Review the commands, hooks and remote servers a plugin declares, choose the bots that can use it, then install it. **Add from your computer** copies a local plugin into Botkins and leaves it off until you review and enable it. Installed plugins have controls for settings, bot access, updates and removal. [Create a plugin](docs/PLUGINS.md).

When a bot needs a password, one-time code or other private value, it can open a **secure input** in the chat. Check the destination and operation, fill the fields or choose a saved credential, then select **Allow this use**. You can also dismiss it. The chat records the request title and the field labels you supplied. The bot gets one-time handles that expire after five minutes or when the turn ends.

In a private owner chat, `find_saved_credentials` can show a bot the names of vault entries saved for an HTTPS site. Use `browser_form` on a Linux screen host to open the site and identify its visible inputs. A desktop chat can use its website side pane. With `request_secure_input`, the person picks a credential in Botkins or on a paired device. The bot passes the one-time handles to `use_secure_input` and receives only the outcome. An approval can also submit an HTTPS form, send a bearer-authenticated GET or check read access to a Git repository. [Linux screen and browser setup](docs/terminal.md#a-screen-without-docker)

In a chat, open **Artifacts** in the side pane to find files a bot wrote, attachments you exchanged and saved exports. Filter by files or media, or include the bot's other chats. Select a row for a preview and use **Go to message** to return to its source. Existing paths in chat open on click. Executables and unrecognized file types are revealed in Finder or Explorer. The [side pane guide](docs/SIDE_PANE.md) describes the phone API and path rules.

Open Botkins.app on macOS. On Windows, extract the entire ZIP and open Botkins.exe. The first time, a welcome page offers three model providers side by side, as equals: **ChatGPT** (the Codex CLI and your ChatGPT plan), **Claude** (Claude Code and your Claude plan) and **GitHub Copilot** (a GitHub account with Copilot access, which includes Copilot Free). None is chosen for you. Sign in to one or more; your browser opens for each, and a provider whose tool isn't on this computer offers **Get it** instead. A provider whose tool is already signed in on this computer is connected without asking again. One connected provider is enough to choose **Get started**, and your default model is the recommended model of the provider you connected first (with several already signed in: the first in alphabetical order; change it in Settings → General). Other providers are under **More providers**. Botkins never sees a password: each provider's own tool keeps its sign-in. Check or change providers later in **Settings → Model providers**, which also opens from **Models** in the sidebar.

A new workspace has no bots. After you sign in, Botkins looks in your Copilot folder for the custom agents you already use (`~/.copilot/agents`, or `$COPILOT_HOME/agents`) and offers them as bots. Tick the ones you want and choose **Add bots**: each becomes a bot with the agent's instructions and, when your account has it, the agent's model. If you have no agents, or choose **Create a new bot instead**, Botkins opens the Create a bot form. Botkins copies an agent and never changes your Copilot files, so later edits to an agent file don't reach the bot. A bot uses the Skills, MCP servers and approvals you set in Botkins, not an agent's own tool list.

**Upgrading from an earlier build.** Botkins was renamed during development. If you used an earlier build under the old name, your bots, chats, wiki and settings are still here, and two things are worth knowing:

- **Your data folder is renamed.** Botkins keeps its data in a "Botkins" folder in your application data folder. The installed app renames the earlier build's folder to "Botkins" once. It does this in one step with nothing copied, and leaves a link under the old name pointing at the folder, so paths saved under the old name still work. A bot's working folder no longer has the old name in it. Botkins does not rename the folder while another copy of the app is running on it, or when a "Botkins" folder with anything in it already exists. It then goes on using the folder where it is. A chat that Claude Code or OpenCode ran continues from Botkins' own copy of the conversation afterwards.
- **On a Mac, the keychain asks once.** The first time you open Botkins, it tells you that it needs the keys the earlier build saved, and then macOS asks whether Botkins may use that build's "Safe Storage" keychain entry. Enter your password and choose **Allow**. That is how Botkins opens your saved credentials and paired phones, and once is enough: Botkins then keeps them under its own keychain entry. If you choose Not now, or say no to macOS, the credentials stay locked and untouched, and Botkins asks again the next time you open it. Windows does not ask.

Template files you exported from an earlier build still import. Environment variables are now `BOTKINS_…`, and the earlier spellings still work. Pages that bots wrote with the earlier bridge names (including `window.bighelp`) still run. New pages use `window.botkins`.

- **Start on Home.** Home asks one thing, **What’s on your mind?**, above the message box, with your primary Botkin beside it. Type and send to chat with that bot. Below, **Your Botkins** shows every bot: click one to open its latest chat, or choose **Add bot**. The **Bot tools** button beside Add bot opens search, the All, Pinned and Hidden filters and **New section**. A chat that waits for your answer appears under **Needs you**. Your recent chats are on **Chats**, and the open side menu shows each bot's latest line.
- **Create a bot** from Home or Chats. Choose **Start from template** for Marketplace and saved templates, or **Import** for a template file or an agent found on your computer. You can also fill in the blank form yourself. Instructions hold up to 30,000 characters, the same as a Copilot agent's prompt. A bot is drawn as a Botkin. In **Bot Studio**, pick one of the 30 characters and one of the 7 palettes (Original keeps the character's own colors), or one of the named color templates, or four colors of your own (shell, accent, face and eyes) from a color picker with a hex field. Pick one of six eye styles too, or keep the character's own. See it in a live preview, or click **Surprise me**. A new bot gets a character few of your other bots have. A template can supply its own look. A Botkin acts out what its bot is doing: it idles, thinks, plans, looks things up, codes, works, replies and waits for you, and it shows a finished or failed reply for a moment. Click a bot to return to its latest conversation, or choose **New chat** for a separate session.
- **Shape how a bot works.** Ask it to maintain its own `AGENTS.md` for working instructions, `USER.md` for preferences you share, and `IDENTITY.md` for its role and voice. These optional Markdown files live under `files/<bot-id>/` in the workspace data folder and follow the bot into project chats. Changes apply on its next turn. Instructions you enter on the bot’s page take priority over its profile and Botkins’ presentation defaults. The defaults explain inline cards, HTML apps, files in Artifacts, and opening the Screen panel during computer use.
- **Arrange bots.** Drag a bot before or after another on Home or in the side menu. Drop it on Pinned, a section, or Other bots to move it between groups. The primary bot stays first. Right-click a bot for its menu.
- **Talk to a bot.** Settings → Voice has separate pages for Dictation, Reading aloud, Live voice, and Keys and servers. Under Live voice, choose Live conversation or Push to talk for this computer. Hold the talk button or Space during a push-to-talk call. Interrupt stops the bot’s audio so you can speak. Live voice sends recent conversation history, the bot’s instructions and identity notes, the person’s name and user notes to the selected voice provider. A paired phone can also include location when the person enables Location in Device access.
- **Save and share bot templates.** On a bot's page, **Save as template** keeps its role, about text, instructions and look for your next bot, and **Export template…** writes them to a `.json` file you can give someone. In **Create a bot**, choose **Import** and then **Import from file…** to add a template file someone gave you. Botkins shows a note so you read the imported instructions before creating the bot. Template files never include chats, folders, capability sources or credentials. Use a template's **⋯** to export or delete it.
- **Manage your bots** from the **⋯** menu on a bot, or right-click it. Pin a bot, move it into a section, hide it, make it your primary bot (the one on Home), duplicate it or delete it. Deleting a bot also deletes its chats, panels and history. **Bot page** edits its name, role, about text, instructions, look and default model.
- **Organize chats** on Chats. Selecting a bot opens your private **Main chat** with it. Under **Settings → Chat → When you select a bot**, you can also choose the latest chat or **Start a new chat**. This choice stays on the computer. A new chat nobody wrote in is archived when you leave it, unless you pinned it, scheduled something in it or left typed text in its message box. **Start a new chat** opens such an empty chat again, out of the archive if it went there, before it makes another. A scheduled run can deliver to another chat without changing that choice. Chats are grouped as Pinned, Today, Yesterday and Earlier, and a dot marks a reply you haven't read. Use the **⋯** menu on a chat to pin, rename, archive, restore or delete it, or to mark it unread. **Details** in a chat shows the bot and its routines beside the chat.
- **Continue in Main chat.** Compaction, changing providers, and switching forks keep the same chat address. Use **Main chat context** between turns to switch forks or reset the context. A reset keeps the previous conversation as a fork you can return to. Proactive chat signals arrive here by default. Choose **Settings → Chat → Proactive signals → New chat every time** to receive each signal in its own thread. This preference applies to your signals on this host.
- **Follow a bot's work** in the chat. While a bot works, the working rail shows its current activity, elapsed time and tool-call count. Open it to see the work in order. The bot's face in these lines stays still. The message box floats over the end of the chat, and messages scroll under it. A **Tasks** chip shows the bot's to-do list, and **In the background** lists any helpers it started. A reply appears as the bot writes it. When a bot writes a line before a tool call and more after it, the two parts are separate paragraphs. The header shows how much of the context window the chat uses, and **Compact** frees space. The meter counts to the most one request to that model may hold, as the model's own provider states it, whichever harness runs the chat. Open it to see the limits too. If the provider states no limit for a model, the meter uses the number the harness reports. In Settings → Chat, **Steps** can keep calls in the rail (Folded), also show every call in the conversation (Open), or show just the failures there (Failed only). **Thinking and updates** can stay in the rail (Folded), appear in both places (Open), or be hidden (Hidden). Turn **Fold finished steps** on to collapse completed activity to one expandable line such as “Worked for 18s · 3 steps”. Turn it off to leave activity where it appeared. Details opens the full work record. Under **Position after response completes**, choose whether this computer stays at the latest content or shows the beginning of the finished reply. Scrolling away while the bot works keeps your place. Expand the finished work line to see where you steered or answered.
- **Keep typing while a bot works.** Press **Enter** to guide an active Copilot-harness or native ChatGPT reply. Choose **Queue** to send a separate message after it finishes. **Steer now** moves a queued message into a supported reply. Other providers, group chats, slash commands and background work keep the message for the next turn. **Stop reply** explicitly stops the current work. Attach files with **+**, by dragging them in, or by pasting them. Hover over a message to copy it, reply to it, or fork the chat from that point. A reply that failed has **Try again**.
- **Read what bots post** on Today under **Feed**, **Ideas** and **Goals**. Ask a bot to post, or give it a routine that posts. Open an item to read it. Then choose **Discuss**, **Clear**, **Let's do it**, **Turn into a goal**, **Mark done** or **Not today**. **Discuss** opens a new chat with the bot that posted the item and puts "Let's talk about this." in the message box, with the item attached as a card, for you to edit and send. On an idea, **Let's do it** opens the chat and sends "Let's do it!" with the item at once (see **Mention records in a message**). Thumbs up and thumbs down tell the bot what helps.
- **Use an app a bot made.** A bot can show a small interactive page, such as a calculator, form or checklist, as a card in the chat. **Open app** opens it in its own window. The window has no network access and can't reach your files, and Botkins asks before an app opens a web page in your browser. When an app sends an answer, the answer waits in your message box until you send it.
- **Chat with several bots at once.** In **New chat**, tick two to six bots and choose **Start group chat**. Each bot answers in turn and sees what the others said. Type `@` and pick a name to ask one bot, or use `@everyone`.
- **Let bots help each other.** With **Teamwork** on (Settings → Teamwork, on by default), a bot in a one-bot chat can ask another bot for the part of a request that fits its role. The helper sees only the message written for it, works with its own instructions, skills and memory, and its answer comes back to the bot you are talking to. The chat shows who was asked and what they are doing; click the row to read the exchange. A bot can ask up to eight times per reply, a helper can't ask further bots, and anything a helper needs approved is asked in your chat. In a project chat, only a bot that may use the project can be asked. Turn Teamwork off for everyone, or keep single bots out of it.
- **Ask a bot on another computer.** Sign both computers into the same owner profile, connect each computer to the profile, and turn on Teamwork for both bots. In a private chat, ask for the bot and computer by name, for example “Ask Scout on Studio to review this paragraph.” The target computer shows the exact outgoing message on an approval card. **Allow this time** covers one request. **Allow for today** lasts until midnight on that computer. **Always allow** remembers the source bot, destination bot and both computers. **Deny** ends this request. The reply appears in the original chat. Clear remembered approvals on the target to ask again, or use `botkins tools forget-approvals --chat <dispatch-chat-id>` there for one pair. For the proposed unattended device setup, see [Node Host setup](../docs/node-host.md).
  The destination runs the approved message in an isolated session. Direct Codex needs CLI 0.171 or later and a configuration that permits isolation. An external ACP agent that cannot restrict its tools needs a different harness for incoming requests.
- **Mention records in a message.** Type `#` to pick a project, a wiki page or a file from the bot's workspace (its own folder and, in a project chat, the project folder). The bot receives the project's details, the page's text or the file with your message. A message can also carry an item from Today (a Feed item, an idea or a goal). Today's **Discuss** and **Let's do it** attach one, and a phone can too. The message shows a "From Today" card that opens Today. The bot gets the item's title, text, links and id, and any chat may be told of an item, whichever bot posted it. In a group chat, type `@` to ask one of its bots. Mentions respect each bot's access.
- **Keep a wiki with your bots.** **Wiki** holds what the team knows as Markdown pages, in sections for Goals, Projects, People, Meetings and Playbooks.
  - **Read.** A page shows its text, and beside it the pages it links to, the pages that link to it, its project record, and links to pages nobody has written yet. Search covers every page. **Activity** lists every change and who made it.
  - **Edit.** **Edit** opens a rich editor: headings, lists, task lists, tables, quotes, code, links, and **Link to page** to pick another page. Save with the button or Cmd/Ctrl+S. If a bot changed the page while you were editing, Botkins asks which version to keep. Quitting with unsaved edits keeps them as a draft that the Wiki offers back. **History** in a page's menu shows earlier versions and restores one.
  - **Shape it.** Add, rename and delete sections, move and rename pages (links follow), and edit a section's template, which is the outline its new pages start from. **How this wiki works** is the guide your bots read before they write; change it to change how they work. On Home, Botkins offers to add pages for projects that have none.
  - **Let bots keep it current.** Tell a bot what happened ("we met Contoso, the renewal moved to March") and it updates the right pages and links them. Ask a question about a project and it looks in the wiki first. Bots can also add sections and reorganize pages. Home has **File something into the wiki** and **Tidy the wiki** to start those jobs, and a page has **Ask about this page**.
  - **What bots may do.** With access limited in Settings → Access, a bot uses only the pages about projects it has access to: a project's own page, and pages that link to one. Only a bot with access to everything can change the guide or a template. In routines, tasks and panel refreshes, and while helping a teammate, a bot can read the wiki but not change it.
  - **Export.** **Export…** saves the whole wiki, one project with everything related to it, or one page with what it is linked with. Botkins lists the pages first so you can leave some out. Save it as Markdown files in a zip, as one web page, or as a PDF.
  - **The files are yours.** Pages are plain `.md` files in the `wiki` folder of Botkins' data (a page's menu has **Show in Finder**), with relative links that also work in other Markdown apps. Deleted pages go to a `.trash` folder there.
- **Give every bot a memory.** Each bot keeps a `MEMORY.md` of durable facts: your preferences, names, decisions and corrections. It reads the file at the start of every conversation and updates it with its memory tools, or when you say "remember that…". A bot changes its memory only in a chat you are part of: in routines, tasks and panel refreshes, and while it helps a teammate, it can read its memory but not write to it. Read, edit or clear a bot's memory in Settings → Bots & capabilities → **Memory**, or from the Memory card on its page.
- **Organize work in projects.** Work → **Projects** lists workspaces for your work by name. A project page has an Overview, a To-do list, its Chats (start one with any bot that has access, or add chats that already exist with **Add a chat…**; **Remove from project** in a chat's menu takes one out), its Artifacts (files your bots made or were given, attached here with **Attach an artifact…** or from an artifact with **Add to a project…**), its Today panels, Access, and Changes when it has a git folder. A bot chatting in a project knows the project, and can read and keep the to-do list.
- **Control what bots can see.** By default every bot can use every project. Turn that off in Settings → Access, then grant each bot all projects, or chosen ones, on its page under **Access**. Taking access away deletes nothing: the bot's chats in that project show why they can't take new messages.
- **Work in a project folder.** In **New chat**, tick one bot and pick a project, or choose **Add folder…**. The bot works in that folder. Choose **Default** to have it ask before risky steps, **Plan** to have it write a plan without changing files, or **YOLO** to let it run tools without asking, in that chat only. **Changes** in the chat header shows the branch, the changed files and each file's diff, and **Commit…** stages and commits everything. Nothing is pushed.
- **Give bots tasks** under Work → **Tasks**. Tasks move through Later, Ready, Working, Needs you and Done. A Ready task with a bot starts on its own when that bot is free, and up to two tasks run at once. A finished task waits in Needs you until you choose **Approve** or **Try again**. Ask a bot to "add that to my task board" and it adds the task itself. A bot does not set the status of the task it is working on: the task moves to Review by itself when the reply ends, with the reply as its result, and you mark it done. If a bot marks its own task done or hands it in for review anyway, the call succeeds and tells it so; nothing fails.
- **Read rich replies.** Messages render GitHub-flavored Markdown: tables, task lists, strikethrough, footnotes, headings, quotes and callouts such as `> [!NOTE]`. A code block shows its language, is colored when the language is known, and has **Copy**. A wide table scrolls inside its own frame. HTML in a message is shown as text, and an image is shown as a link, because the app never loads remote content into a chat.
- **Read and hear replies.** Turn on link previews in Settings → Appearance to show a card for the first web link a reply shows. Botkins fetches the page from your computer, so previews are off by default, links hidden behind Markdown text are never fetched, and private and local-network addresses are never contacted. **Read aloud** in a message's actions speaks it, and Settings → Voice can read every new reply aloud (see **Talk and listen** below). Cards and panels can also show progress bars, badges and line charts.
- **Talk and listen.** **Settings → Voice** has three choices, shared with your paired phones. **Dictation** turns speech into text in the message box: the microphone button uses this computer's own dictation by default (on a Mac the system's Dictation, which you may need to switch on under System Settings → Keyboard; Windows and Linux have none an app can start, and on Windows the Windows key + H dictates into any box), or records and sends the recording to OpenAI, Azure, ElevenLabs or your own speech server. The words land where the cursor is and are never sent for you. **Reading aloud** speaks a reply with this computer's voices, or with OpenAI, Azure, ElevenLabs, Gemini or your own server, with a voice and a speed you choose. **Live voice** is a spoken conversation with a bot: when the message box is empty, the send button is a **Live voice** button (once you type, it is Send again, and while a bot works it is Stop). It needs a provider chosen first: your ChatGPT sign-in, or a key for OpenAI, Gemini or ElevenLabs. The voice only talks; for anything beyond small talk it hands your request to the bot as a normal message in the chat and speaks the answer. A bot can have a voice of its own: on its page, **Voice** sets who reads its replies and who talks in live voice with it, with a provider, model, voice and speed, or **Same as Settings**. The keys stay in Settings → Voice. A bot that reads with this computer keeps its system voice in this window only. Keys are saved on this computer, shown only as **Saved**, and never sent to a phone. A key is kept with the address it was given for: changing a provider's address removes its saved key, and the page asks for the key again, so a key is never sent to an address it wasn't given for. Botkins has no speech engine of its own built in: to use local models, run any OpenAI-compatible speech server and choose **Your own server**. Of all this, only live voice on a ChatGPT sign-in has been used with a real service so far; the others have been run against stand-ins.
- **Create a routine** under Work → **Routines**, or ask a bot to schedule one. Choose Once, Daily, Weekdays, Weekly or a custom schedule. New desktop routines start with **No output**. The bot does the work and Work records whether it finished. To receive a result, choose the routine’s chat, a specific chat with the bot, or Today’s Feed, Ideas or Goals. You can turn off completion notifications separately. A routine with a destination can also finish quietly when there is nothing to report. Open its detail page to inspect past runs, edit the schedule, pause it or run it now.
- **Get notified** when a routine finishes, a bot needs an answer, or a reply arrives while Botkins is in the background. Set notifications and quiet hours in Settings → Notifications. **Usage**, under Work or Settings, shows turns, tokens and cost by day, model and bot, and exports them as CSV.
- **Use another computer's Botkins from this one.** On the other computer open **Settings → Phone**, turn on access and choose **Pair**. On this computer open **Settings → Computers and teams**, choose **Connect another computer**, paste the pairing link (or type the other computer's address and the code) and press **Connect**. On a first launch, **Connect to another computer** does the same and opens on that computer. Then choose that computer in the side menu's switcher: the window shows its bots, chats, tasks and Today, a line across the top says whose they are and how it is connected, and **Use this computer** takes you back. Botkins remembers the computers you paired and which one you were on, so it opens on that computer again after a restart. Your own workspace here is untouched while you are away. The other computer lists this one under **Devices** (Settings → Phone), where it can be renamed or removed; a removed computer is told at once. A few things can only be done on the computer itself (pairing phones, signing a provider in, choosing folders); they say so when you try.
- **Invite people to a team.** **Settings → Team** manages join requests, invite codes, members, groups and roles. An invite shows its code, its link and a QR code of the link that the phone app scans from Join a team. **Invite** in a chat's header opens **People in this chat**, with a switch for each person on the team: a chat's replies and questions go only to whoever started it and those invited into it. A role chooses the actions and bots a member may use. A member joins from **Settings → Computers and teams → Join a team** (or **Join a team** on a first launch), the owner approves the request, and Botkins keeps that pairing separate from full-trust computer access. Member messages are labeled with the person's name and carry that identity into bot turns, while unavailable settings and actions stay out of the member's view. A turn runs with the tools both the chat's creator and the message's writer may use. A routine a member makes is theirs: it runs under their limits and its result goes only into a chat they are in. A member can mention only files from chats they are in, never your projects or wiki pages, and this computer alerts you only about chats you made or were invited to (a request only you can approve still reaches you).
- **Let a bot use the side pane.** A bot can open the pane beside the chat and show a table, a page it wrote (a chart, a form, a small tool), a website, or the Screen panel. Each one is a tab, with the bot that opened it, and earlier ones stay. Close a tab, pin one so it stays in front and is never dropped, or close the pane: for the rest of that reply the bot won't open it again, and a new panel waits as a tab. A page a bot wrote runs in a sandbox with no network. A website opens in the app's own viewer, which stores nothing on your computer, can't reach the app, asks for no permissions and downloads nothing; depending on the chat's approval setting you are asked before a bot opens one. The Screen panel shows the same switch as Settings → Phone; a bot can only show it.
- **See what is left of your plans.** **Usage** starts with **Plans and limits**: one card for each provider you have connected, with the plan's name (such as Claude Max 20x, ChatGPT Pro or GitHub Copilot Pro+), how much of each limit is left, and when it resets. The model picker shows the same in one line beside each provider's name, such as “62% of weekly left · resets Mon”. The numbers come from each provider's own tool with the sign-in it already has; a value a provider doesn't give says **Not available** and has no bar. An API key has no plan limits and says so. Each card says when it was last read, and **Refresh** reads every provider again.
- **Create a panel** on Today, choose its bot, and describe what to show. For example, “Track my weekly writing goal with a word-count metric and a table of drafts. Refresh it at 9 AM on weekdays.” Bots can publish metrics, Markdown, lists, tables and bar charts. Each bot manages its own panels.
- **Ask for a custom view.** A panel, or a card in a chat, can also hold a page the bot writes in HTML: a chart, a dashboard, a timeline, a small tool. Ask for it in words, such as “show my pipeline as a bar chart”. The page is drawn inside the panel, follows the app's light and dark colors and sizes itself. It runs in a sandbox: it can't reach the network, your files or the rest of the app. It can put text into your message box for you to send, and it can ask to open a web page, which Botkins confirms with you first. On a refresh the bot can replace only the page's data, so routine updates stay quick.
- **Manage a routine** from the panel’s menu or by asking its bot. A routine has a five-field cron expression, an IANA time zone and refresh instructions. Each refresh uses one model turn. Use the panel’s refresh button to run one now, or open Work to inspect the result. An update time records an actual content write. The last check records the outcome of the refresh.
- **Resume after a restart.** If Botkins closes during a chat, it reopens the same conversation and Work item on launch. A surviving Codex turn can finish in place. When the provider lost the turn, the bot continues from the saved request and its conversation history. Group chats skip members who already replied, and queued messages follow the recovered reply. Stop cancels recovery for that turn. A command interrupted while changing settings may ask you to check its result.
- **Keep Botkins running** under Settings → General → Background. **Keep running when the window is closed** is on unless you switch it off. Closing the window then leaves Botkins running with its icon in the menu bar (macOS) or the taskbar (Windows, Linux), so a phone and your routines keep working. Quit from that icon, which also exits the scheduler. **Run at startup** is off unless you switch it on. Botkins then starts without a window when you sign in to the computer. On wake or next launch, due panels receive one catch-up run each. A sleeping or powered-off machine runs its checks when it is next available. A tool requiring interactive approval needs an open Botkins window.
- **Type `/`** in the composer to search the chat’s commands, skills and tools. The list also has the commands of the harness that runs the chat: Copilot’s built-in and extension commands with the Copilot SDK harness, and, with Provider default, Claude Code’s own commands on a Claude model. Use the arrow keys and Tab to complete a name. Press Enter or click to select. Try `/model` for the chat picker, `/permissions` for the chat’s approval level, or `/btw <question>` for a side answer based on the conversation. ### Provision an MCP OAuth client

Register Botkins as a public native client with the authorization server. Enable the authorization code grant with PKCE (S256), register the loopback redirect URI, and approve the scopes your users need. Install a UTF-8 JSON file named `mcp-oauth-clients.json` on the computer running Botkins. The following example uses illustrative values. Replace them with the registration issued for your deployment.

```json
{
  "clients": [
    {
      "serverUrl": "https://tools.example.com/mcp",
      "issuer": "https://login.example.com",
      "clientId": "your-registered-client-id",
      "redirectUri": "http://127.0.0.1:47823/callback",
      "scopes": ["tools.read"]
    }
  ]
}
```

| Platform | Default file |
| --- | --- |
| macOS | `/Library/Application Support/Botkins/mcp-oauth-clients.json` |
| Windows | `%ProgramData%\Botkins\mcp-oauth-clients.json` |
| Linux | `/etc/botkins/mcp-oauth-clients.json` |

Alternatively, set `BOTKINS_MCP_OAUTH_CLIENTS_FILE` to an absolute file path in the desktop process’s launch environment. Give the app read access and restrict writes to administrators. Botkins reads the file at sign-in. A profile matches the configured server URL and the discovered OAuth issuer, including their paths. Specify each required scope as a separate string, or use an empty array to omit the scope parameter. Use a fixed HTTP loopback callback on `127.0.0.1`, `[::1]`, or `localhost`, with a path and no query or fragment.

The person chooses **Sign in** and finishes in their browser. A client ID entered under **Advanced** takes precedence over the profile. For a confidential client, use the existing manual configuration, which stores the secret in the credential vault.

**Trial runs.** To try the app without touching the installed one, start it on a data folder of its own with `BOTKINS_DATA_DIR=<folder>`. The tests and smokes do. These variables set up such a run:

- `BOTKINS_DATA_DIR` names the data folder. The data folder rename of **Upgrading from an earlier build** never runs when it is set.
- `BOTKINS_LINK_PORT` is the port the phone link listens on, so a trial run never takes the installed app's.
- `BOTKINS_PUSH=1` lets a trial run send notifications to phones through the Botkins relay. Without it, a run on a data folder of its own sends nothing to the relay for that (the link refuses the request), so a test can't ping a real phone.
- `BOTKINS_NEARBY=1` lets a trial run announce itself on the local network. Without it, such a run stays quiet, so it doesn't appear in a phone's list of computers.
- A trial run never touches the system keychain, so it can never put a keychain question on the screen of whoever is using the computer. Its Copilot runtime is handed a token (`BOTKINS_COPILOT_TOKEN`, else the GitHub CLI's) or runs signed out, and its vault and phone link keep their key in a file in the trial's own folder, also in a packaged build. `BOTKINS_COPILOT_SIGNIN=keychain` and `BOTKINS_KEYCHAIN=1` ask for the keychain, each for a deliberate check.

Set `APPLE_API_KEY_ID` and `APPLE_API_ISSUER` for notarization. Run `npm run package` to sign the app. The app uses the hardened runtime and the entitlements in `build/entitlements.mac.plist`. The bundled Copilot runtime has its own signature. To verify the release, run `spctl -a -vvv -t exec release/<version>/mac-arm64/Botkins.app`. Look for `source=Notarized Developer ID`.

For Windows, select the signing account with `BOTKINS_SIGN_ACCOUNT`. Set `BOTKINS_SIGN_PROFILE` and `BOTKINS_SIGN_PUBLISHER` to the certificate profile and publisher. Run `npm run package:windows`. For an unsigned test build, set `BOTKINS_SIGN=off`.

### Updating the desktop app

Open **Settings → About → Check for updates**. The installed app also checks GitHub Releases shortly after launch and every six hours. A newer stable version triggers a desktop notification. On a Mac with a matching ZIP, **Update and restart** downloads the release, verifies it and relaunches Botkins. Your workspace stays on disk. A bot can use `check_app_update` and, when you ask it to update, `install_app_update`. The restart waits for that chat turn to finish. On platforms distributed as portable archives, About links to the release downloads.

On macOS, turn on **Install updates automatically** in About to install a signed release when your bots are idle. Botkins remembers the choice after a restart. You can download releases and check for updates without signing in to GitHub. Trial data folders skip automatic checks.

**Prepare a release draft.** Starting with the first release after 0.16.4, the desktop and terminal hosts ship together. On the Mac signing host, check out the clean commit tagged `v<version>` on GitHub, run `npm ci` in `desktop/`, then run `npm run release`. To use prepared notes, pass `-- --notes /path/to/notes.md`. Otherwise GitHub generates them. The command uses the signing configuration above, the GitHub CLI with release write access, GPG, and osslsigncode with trusted Windows signing and timestamp roots (`BOTKINS_WINDOWS_CA_FILE` can point to a PEM bundle).

The command builds all platforms, checks the Mac signature and notarization ticket, verifies Windows Authenticode, and checks the signed manifest. It uploads 16 files to one draft, including the four terminal tarballs and `install.sh`. It compares the uploaded digests with the local files and runs `node scripts/check-release.mjs <version>` against the draft. After a transfer failure, use `npm run release -- --resume` in the same checkout. It rechecks the packages and uploads the missing files.

**Publish.** Once the draft is approved, run the gate again immediately before marking it Latest. Replace `VERSION` with the package version in both arguments.

```sh
node scripts/check-release.mjs VERSION && gh release edit vVERSION --repo promptclickrun/Botkins --draft=false --latest
```


## Implementation

Electron hosts a sandboxed TypeScript/React renderer, which reaches the workspace through a preload bridge. `desktop/start.mjs` is the main file, and it loads `desktop/main.mjs`. Bot settings, displayed transcripts, panels, schedules, memory and work history live in Electron’s per-user application data directory. The desktop process owns the scheduler and panel writes. It checks panel ownership and revisions before replacing content.

**The workspace and its host.** `desktop/runtime.mjs` builds the workspace as one running thing: the model providers, the calls the window and a paired phone make, and the phone link. It is plain Node and never loads Electron. Whatever needs a window, a dialog, the keychain or the screen is asked of a host (`desktop/host/index.mjs` lists every member). `desktop/host/electron.mjs` is the desktop app's host, and `desktop/main.mjs` keeps what is the app's own: Electron's start, the window, the tray icon and the calls only the window makes. `desktop/host/headless.mjs` is a host with no window and no display: it refuses what needs a desktop with one sentence (“… is not available on this host.”) and guards secrets with `desktop/host/keystore.mjs` in place of the keychain. `checkHost` refuses a host that leaves a member out, so a member added to the interface can't be forgotten in one of them. `test/host.test.mjs` and `test/keystore.test.mjs` cover both; `test/fake-host.mjs` is the host the tests answer and watch.

**The terminal host.** `botkins serve` (`cli/botkins.mjs`, the package's `bin`) runs that workspace as a service under plain Node, with no Electron and no display. `desktop/terminal/serve.mjs` puts it together: the settings in `config.json` (`config.mjs`, checked whole before they are used), the log (`logs.mjs`, which replaces anything that looks like a credential before a line is kept), the key store, and the control socket (`socket.mjs`). The socket is a Unix socket of mode 0600 in a folder of mode 0700, so only the user the service runs as, and root, can connect; whoever connects is the owner. Every other `botkins` command is a client of that socket (`cli/commands/`), prints one JSON document with `--json`, and never opens the data folder's files while the service runs. `control.mjs` holds the calls; `signin.mjs` signs a model provider in without a browser on the host (a one-time code, the tool's own sign-in passed through the terminal, or a pasted token sealed in the vault). `test/terminal-service.test.mjs` runs a whole service with a stand-in agent as its provider and a stand-in phone (`test/fixtures/standin-agent.mjs`, `test/fixtures/phone.mjs`), each a real process; `test/terminal-cli.test.mjs` and `test/terminal-config.test.mjs` cover the command line, the settings and the log.

**The dashboard.** `botkins tui` (`cli/tui/`) shows the service, the paired devices, the bots, the chats and runs, the routines and the log on one screen, and does the common edits from the keyboard. It is one more client of the control socket. It uses no terminal interface library: `cli/tui/view.mjs` draws the whole screen as lines of text from one state, with plain escape sequences, and `cli/tui/app.mjs` turns Node's own key events into calls. A library such as Ink would add React and a layout engine to every install and to the memory of a process that draws a header and six lists; this one adds no dependency, and the dashboard's process uses about 65 MB (a Node process that does nothing uses about 40 MB). `test/terminal-tui.test.mjs` draws every tab at several terminal sizes and presses the keys against a stand-in service.

**Installing and updating the terminal host.** `install/install.sh` is the one-line installer: it checks a release's signed checksums before it unpacks anything, adds Node.js when the computer has none, and hands over to `botkins service install`. For the whole computer it first makes the check the updater makes (`notRootOwned` in `desktop/terminal/update-install.mjs`): the install folder and every folder above it are root's own and nobody else's to write to, or nothing is installed, because nothing could be updated there. The running service makes the same check and says so in its update status (a phone shows the sentence, with the commands that fix it), and so does `botkins doctor`. Which release is the latest is read from the release page (`/releases/latest` redirects to it) and the release's own `SHA256SUMS`, not from GitHub's API, which answers an address that is not signed in only 60 times an hour; the API is the second try (`latestRelease` in `desktop/updates.mjs`, and the same in `install.sh` and the desktop app's Linux updater). `desktop/terminal/units.mjs` makes the systemd unit (its own user, `ProtectSystem=strict`, the data folder as the only writable path, the host key as a credential) and the launchd job; `desktop/terminal/manager.mjs` installs, starts and stops them with the system's own tools. `desktop/terminal/update-install.mjs` installs a new release beside the old one, only after `verifyRelease` (the desktop app's own Linux updater check, with the same release key) accepts its signed checksums, and puts the old one back when the new one doesn't stay up. Between the switch and the restart it has the new version write the service's files (`botkins service refresh`, `refresh` in `manager.mjs`): a release may change what the unit says, the updater that runs is always the old version's, and what was chosen at install time (the user, the data folder, the `--allow-path` folders, where the host key comes from) is read back from the installed file by `units.mjs`, never guessed. Environment variables and write folders a person added are carried into the new file; a file with any other setting of theirs is left as it is, and `botkins doctor` names it. A version that stops writing a line, or writes it differently, lists the earlier line in `ONCE_WRITTEN` in `units.mjs`, so the next version knows it for Botkins' own; `test/fixtures/service-files` holds what each release wrote, and a test fails when one of those files is no longer read that way. The earlier files go back with the old version, and `botkins doctor` says when the installed files are not the ones this version writes. The service itself can only ask for an update (`desktop/terminal/updates.mjs`). The install writes how it ended to `last-update.json` in the install folder (root's own; never into the data folder, where a bot's tool could have put a link under any name), which the service reads when it is back, so a phone that asked learns that the update worked or that the old version was put back. The calls a window and an owner's phone make (`appUpdateStatus`, `checkAppUpdate`, `installAppUpdate`, `setAppUpdateAuto`; the capability `app-update-v1`) are in `desktop/runtime.mjs` and answer with `AppUpdates.status()`: the state, `auto` on a host that can install by itself (the setting `updates.auto`, off unless switched on), and `last`. A check that finds a newer version tells the owner's phones through the link, once for each version. `scripts/package-terminal.mjs` builds the tarballs, and `scripts/package-linux.mjs` calls it so the release's one signed `SHA256SUMS` covers them. The `terminal` stage of the `Dockerfile` is the same service as a small image, and the default of `docker compose up`. `test/terminal-install.test.mjs` and `test/terminal-refresh.test.mjs` cover all of this with stand-ins for the system tools, and `test/terminal-root.test.mjs` runs what root does beside another user's folder as root (CI runs it with `sudo`). `test/terminal-e2e/units.sh` (Linux, in a container with systemd) and `test/terminal-e2e/macos-update.sh` (macOS, with launchd) do whole updates through three versions with changed service files, from a mirror and a key of the run's own: the service is asked, the updater downloads, checks and installs, the service files follow the version, and go back with it. `test/terminal-e2e/run.sh` runs the real installer in a clean Debian container with systemd, then pairs a stand-in phone on the local network and through the relay, and restarts the service and the container. `test/terminal-e2e/from-release.sh --from <N-1> --to <N>` is the check for after a release is published: on a machine with systemd it installs the earlier release with that release's own `install.sh` from GitHub, asks the service for the update the way a phone does, and ends well only when the service runs on the new one (a release with no terminal build before it is installed fresh). Each release also publishes the `terminal` stage as `ghcr.io/promptclickrun/botkins`, which `docker-compose.yml` uses by default; `botkins update` in a container names that image, because a container is replaced, not updated from inside.

**Bots as Botkins.** The design kit is in `design/botkins-kit` as delivered: the characters, the palettes, the motion spec, the fonts and the color tokens. The app's page uses the kit's own renderers (`customize.js`, `motion/catalog.js` and `motion/render.js`). A small plugin in `vite.config.mjs` serves them unchanged as one module, `virtual:botkins-kit` (typed in `src/botkins-kit.d.ts`). `src/botkins.ts` asks it for an animated SVG for a character, a palette and a state, and `src/Avatar.tsx` shows that SVG in an `<img>`. A small avatar in a list stays still until its bot is busy, and reduced motion holds every pose. The look of a bot is `bot.look` on the bot itself in the workspace file, so this computer and every paired phone show the same character. It is `{ head, palette }`, with two optional parts: `eyes` (one of the kit's styles; "oval" is every character's own and isn't saved) and, when `palette` is `"custom"`, `colors` as `[shell, accent, faceplate, eyes]`, four `#rrggbb` values. Colors are dropped from a look in a kit palette. The rules are the phone link's, so a look saved on either side means the same on both. `desktop/looks.mjs` checks a look, picks one for a new bot (a character few of the others have), and gives a bot without one its look on load. `LOOKS_CAPABILITY` (`looks-v2`) is the name a phone asks about before it offers eyes and custom colors. `src/lookRender.ts` turns a look into the options of the kit's renderer: a custom look passes its four colors, and a bot's own eyes replace only the default open eyes, so a state with an expression of its own (listening, completed) keeps it. A custom look without four valid colors draws as Original. `src/BotStudio.tsx` is the chooser and `src/ColorPicker.tsx` the color picker, whose color math is the phone app's. A phone changes a look through the link's `setLook`, which the app saves on the bot. On the first start, looks that an earlier phone link kept in `link/link.json` are taken over onto the bots. The `avatar` and `face` fields of earlier versions stay in the file, and nothing draws them. A template carries `look` instead of an avatar.

**Look.** The themes and fonts are the phone app's, value for value. `scripts/build-themes.mjs` holds the phone's own theme code (its `src/ui/themes.ts` with the types taken out): the Botkins theme is the kit's tokens with the steps the phone added between them, Ink is written out, and the others come from a hue and an action color through `makeTheme`, which builds them in OKLCH (the page, menu, lines and bubble lean toward the hue; dark mode is a night in it) and keeps every text color readable. The script writes `desktop/themes.json` with the themes and the font list; `node scripts/build-themes.mjs --check` fails when that file is out of date, and to follow a change on the phone you copy its file into the script again. Both the desktop process (`desktop/preferences.mjs`) and the page (`src/themes.ts`) read the file. The page gets a theme as CSS custom properties on the root element (`src/appearance.ts`, `src/tokens.css`): `--accent` fills, `--accent-text` is the action color as text. It remembers the last appearance so the next launch draws in the right colors at once. `appearance.themePicked` records that the person chose a theme; until then the theme is Ink, whatever was saved (`appearanceField`). `appearance.darkColorTheme` is a theme dark mode wears instead (null for one theme in both), and `appearance.contrast` (0 to 100) moves lines and quiet text toward the ink (`withContrast` in `src/themes.ts`); Settings › Appearance draws each theme as a small picture of the app, its light and dark halves split on a slant. `appearance.fontPicked` records that the person chose a font; until then it is the system's face (`system`). A file from before that was recorded keeps any saved font but `botkins`, which was saved for everyone. A font other than the kit's pairing sets one family for body and headlines; a face the system lacks is not offered, and a saved one draws as the system's face. Georgia has no medium weight, so `src/tokens.css` draws its medium weights with the regular face. The fonts that ship are in `src/fonts`. Icons and marks are built from the artwork in `assets/brand` by `node scripts/build-brand.mjs`, which needs Python with Pillow. The icons of the six places are the navigation pack in `assets/brand/nav-icons`, one SVG a place; `src/PlaceIcon.tsx` puts each file's shapes on the page in the text color, so replacing a file changes the icon. With icons only (`sidebar.collapsed`, the usual menu), a place is a 24px icon in a 48px button and its name shows on hover and on keyboard focus. `sidebar.picked` records that the person opened or collapsed the menu themselves; without it the menu shows icons only, whatever was saved (`sidebarField` in `desktop/preferences.mjs`).

**Wiki.** `desktop/wiki.mjs` keeps the wiki as files under `<data>/wiki`, in the "LLM wiki" pattern: `WIKI.md` (the guide), `index.md` (a catalog of every page) and `log.md` (the change log), with sections as folders and a `_template.md` in each. Botkins writes the index and the log itself. Bots work through `wiki_search`, `wiki_read`, `wiki_write`, `wiki_edit` and `wiki_organize`. Links are stored relative to the page; `[[Name]]` and paths from the top of the wiki are converted when a page is saved. Paths are checked against links out of the folder and against a second spelling of an existing name, and each change keeps the earlier text in `.history` (20 versions per page). The editor (`src/WikiEditor.tsx`, Milkdown Crepe) loads only when a page is edited.

**Credentials.** `desktop/vault.mjs` is the only place a secret is stored: AES-256-GCM per entry under a vault key, which the installed app wraps with the system keychain (Electron `safeStorage`); a development run keeps the key in a file in its own data folder. The workspace file holds references (`vault:<id>`), and the app's page receives neither secrets nor references. A vault that can't be opened (another computer, or the installed app's vault in a development run) is left untouched until it opens again or the person resets it. `desktop/oauth.mjs` signs in to remote MCP servers: discovery (RFC 9728, RFC 8414), dynamic client registration (RFC 7591), authorization code with PKCE on a loopback address, the `resource` parameter (RFC 8707), refresh with rotation. What a server says about its sign-in is checked before it is believed: its description must be about that server, the sign-in server must name the address it was fetched from, the sign-in page must be on that sign-in server, and a server on the internet can't point Botkins into the local network. A provider asks for a token through the `mcpAuth` function of a session's spec. A bearer token is always sent spelled "Bearer" (`scheme` in `desktop/oauth.mjs`), whatever the sign-in server called it, because Composio refused "bearer". A kind of token other than bearer is left as the server named it. The credentials a bot can be given when it asks for a secret are the phone link's (`link.credentials`, `desktop/link/credentials.mjs`, with the password managers in `managers.mjs`), kept in their own encrypted file beside the link's. `desktop/savedcredentials.mjs` gives this window the same calls a phone has, as page-only handlers that return labels and states and never a value, and `respondArgs` fills a `{ $credential: id }` answer in on this computer just before it reaches the workspace, as the link does for a phone's answer. The page is `src/SavedCredentials.tsx`, and `src/CredentialPicker.tsx` in the request panel. A trial run looks for the managers' command-line tools only in the folders `BOTKINS_TOOL_PATH` names (nowhere when it isn't set), so a test never runs a real password manager. `test/savedcredentials.test.mjs` and `test/credentials-smoke.mjs` use stand-ins.

**Phone access.** `desktop/link/` is the Botkins link, which lets Botkins on a phone use Botkins on this computer. Its files are copied unchanged from the phone app's repo (`link-host/`; see `desktop/link/README.md`), so change them there and copy them again. `desktop/main.mjs` makes one `LinkHost`, and it listens only while Settings → Phone is switched on. The link uses plain HTTP on the local network or a tailnet, and encrypts every message itself, so it needs no certificate: X25519 key agreement, HKDF-SHA256, and ChaCha20-Poly1305 under a numbered nonce that is accepted once. Electron's Node is built on BoringSSL, which has no ChaCha20-Poly1305 cipher, so `desktop/link/crypto.mjs` (copied from the phone repo's `link-host/`) seals with `@noble/ciphers` there, the library the phone uses. Plain Node uses its own cipher. Pairing failed in the real app for this reason while every test on plain Node passed, which is why `test/link-electron.test.mjs` runs the host under Electron. A pairing code (twelve characters, good for one phone, five minutes and eight tries) salts the first shared key, and the QR code carries the computer's public key so the phone knows it is talking to the right computer. Each session then mixes a fresh key exchange into the phone's key. The link refuses callers outside the local network and tailnet, and any request that comes from a web page. It also limits what one address may do: 24 connections at a time (256 in all), a connection that says nothing is dropped after ten seconds, and tries at pairing and at opening a session are counted per address. A phone holds at most six sessions and eight unfinished uploads. A credential reference from a phone is filled in only at fixed places (the value of an answer, an MCP server's environment values, headers and client secret, a provider service's key), and a mentioned file's path may not climb with `..`. A phone may only make the calls in `REMOTE_METHODS` (`desktop/link/methods.mjs`): they leave out anything that opens a window, a file dialog, the shell or the clipboard on the computer, and anything added later until it is listed. The calls the Phone page makes (`phoneLink`, `setPhoneLink`, `startPhonePairing`, `cancelPhonePairing`, `removePhone`, `renamePhoneLinkComputer`) are not in that list, so a phone can't pair another phone. The link also offers `link.adoptMcpSignIn`: a phone that signed in to an MCP server with OAuth hands over its own tokens, and `McpOAuth.adopt` (`desktop/oauth.mjs`) saves them in the vault after the same discovery checks as a sign-in, using the sign-in server's own addresses and never one the phone names. `link.json` in `<data>/link` holds this computer's identity, its key and the paired phones. In the installed app the private key is wrapped by the system keychain (Electron `safeStorage`), like the vault's key; if it can't be opened, Settings says so and leaves the file alone. `State.phones.revision` goes up when a phone pairs, connects or is removed, so the Phone page asks again. A bot's look is kept on the bot: the backend given to `LinkHost` has `setLook`, so the link stores no looks and sends each bot's own. What a phone may do with the screen is the person's choice (`setPhoneScreen` → `link.setScreenMode`, a call only this window can make, like the others of the Phone page). The pictures come from `desktop/screenshare.mjs`, an adapter on Electron's `desktopCapturer` that the link is given as `backend.screen`: it numbers the displays from the main one, scales a capture to the width the phone asks for, and reports the Screen Recording and Accessibility permissions. For the Screen section of the Phone page it also says what macOS has allowed (`granted`) and, for **Grant**, asks macOS for a permission and opens the page of System Settings where Botkins is switched on (`request`). Windows and Linux ask for neither. Clicks and typing are posted by the link itself (`desktop/link/input.mjs`). When a phone starts watching, `LinkHost` emits `"screen"` and the app shows a notification, whatever the notification settings. The link's own credential vault (`link/credentials.json`) is wrapped by the same keychain hooks as its private key.

`desktop/phonepage.mjs` holds what Settings → Phone is shown and the calls only that page makes; `desktop/main.mjs` gives each a handler of the same name, and none is in `REMOTE_METHODS`. Away from home is `setPhoneRelay` → `link.setRelay({ enabled })` and `resetPhoneRelay` → `link.resetRelay()` (`desktop/link/relay.mjs`; the relay's address is the link's own default, so the app names none). Turning it on needs phone access on, because the relay runs only then. The page is told `{ enabled, connected, problem? }` and nothing else: not the relay's address, and nothing about the Ed25519 key that names this computer's place, which stays in `link.json`, wrapped by the keychain like the link's own key. `LinkHost` emits `"status"` when the connection comes or goes, so the page's line follows it. `test/phonepage.test.mjs` runs a real `LinkHost` against the phone repo's in-memory relay (`test/fixtures/fake-relay.ts`, copied unchanged) with a clock turned by hand; no test opens a socket to the real relay.

**What the app tells the link.** `desktop/main.mjs` gives `LinkHost` a backend with a few more parts than the calls:

- `capabilities` is the `CAPABILITIES` list, the names a phone asks about before it uses a newer feature: `models-v2` (model details in the catalog), `looks-v2` (eyes and custom colors), `routine-delivery-v1` (where a routine's result goes and whether it notifies), `routine-no-output-v1` (quiet routine runs), `routine-owner-v1` (a routine a team member makes carries their id as `createdBy`), `artifacts-v1` (files made or shared with a bot), `board-mentions-v1` (a Today item carried by a message) `provider-usage-v1` (the call `providerUsage`: each provider's plan and limits), `side-pane-v1` (panels a bot shows beside a chat, `docs/SIDE_PANE.md`) `remote-hosts-v1` (this app can itself be a client of another computer), `files-v1` (files answered and taken without a dialog), `folders-v1` (the folder browser) and `project-artifacts-v1` (artifacts attached to a project: the calls `addProjectArtifact`, `removeProjectArtifact` and `projectArtifacts`). A name is added there when a feature needs both sides.
- `attention` says whether this window is visible and focused and, if so, which chat is open in it. The page reports the open chat through the `viewing` handler. The link's push code uses it to hold back a notification for a reply the person is looking at.
- `desktop/phonetools.mjs` makes the bots' tools on a phone. The link lists what the paired phones allow (`link.deviceTools()`, from `DEVICE_TOOLS` in `desktop/link/device.mjs`) and runs a call on the phone (`link.callDeviceTool()`). `PhoneTools` keeps only well-formed tools (`phone_…` names, a description, an object schema), marks a tool as skipping approval only when the link itself says it only looks, leaves out the others in a turn nobody watches, and aborts a waiting call when its turn is stopped. The tools' names, descriptions and parameters are the link's, and `PhoneTools.summary()` gives the app's state how many tools there are and how many only look.
- In Settings → Phone → Devices, the person's name appears above the device model. Use **Add name** for an older pairing or **Change name** to edit it. A team member’s name applies across their paired devices.
- `notified` and `shared` in `src/PhoneSettings.tsx` turn the link's `push` preferences and per-source levels into the two lines under each phone on the Phone page.

A run on a data folder of its own (`home.from === "override"`, set by `BOTKINS_DATA_DIR`) is a trial run, and it differs in two ways. The link's `fetch` refuses a request to the relay's address unless `BOTKINS_PUSH=1`, so no notification can leave (only the relay's address is refused). And the Bonjour announcement stays off unless `BOTKINS_NEARBY=1`. Separately, in any run, the link listens on `BOTKINS_LINK_PORT` when it is set.

**Finding the computer.** `desktop/nearby.mjs` announces this computer on the local network while phone access is on, so Botkins on a phone can list it and nobody types an address. The service is `_botkins._tcp` on the link's port, named with the computer's name, with the TXT values `v` (the link protocol) and `id` (this computer's link id). It says nothing that the link's own `hello` doesn't, and it is not what lets a phone in: that is still the pairing code. On macOS the system's own Bonjour does the announcing, asked through its `dns-sd` tool. macOS lets an app use the local network only once the person allows it (System Settings → Privacy & Security → Local Network), and only an app that goes through the system is asked and told "no"; packets an app sends by itself are dropped without a word. So the app knows when it is refused, and Settings → Phone then shows **Local Network** with a **Grant** button that opens that page. On Windows and Linux a responder written in JavaScript (`bonjour-service`) announces, and nothing has to be allowed. The name is the system's own: on a Mac the one in Sharing, elsewhere the host name without its domain, unless the person renamed the computer in Settings → Phone. A test run stays quiet unless `BOTKINS_NEARBY=1`. A phone that can't hear it (another network, a tailnet, a network that blocks multicast) pairs with the QR code or the typed address.

**Staying on.** `desktop/startup.mjs` holds the two choices of Settings → General → Background (`settings.background`): `keepRunning` (on unless switched off) and `runAtStartup` (off unless switched on). With `keepRunning`, closing the window leaves the app running with its icon in the menu bar or taskbar. `runAtStartup` asks the system for an entry that starts the app with `--hidden`, which opens no window: a launch agent on macOS, the sign-in apps on Windows and an autostart entry on Linux. The entry names the app by its path, so `desktop/main.mjs` writes it again on every start while the setting is on, and a moved or updated app keeps starting. A test or development run writes its entry inside its own data folder, never the system's.

**Routines.** `desktop/routines.mjs` keeps each routine as a `chat.schedules[]` entry with `routine: true` in its own chat. Two optional fields say what happens to a run's result. `deliver` is `{ to, chatId?, category? }`, where `to` is `none`, `routine`, `chat`, `feed`, `idea` or `goal`. The desktop editor saves `{ to: "none" }` for a new routine unless a destination is chosen. A missing delivery field retains the historical routine-chat behavior. A successful run with no output records its completion without publishing a reply or sending a completion notification. `deliveryField` checks it: a chat can be named only with `to: "chat"`, a category only with `goal`, and a named chat must belong to the routine's bot and be an ordinary chat (not a group, routine, temporary, panel, helper or archived chat). `notify` is saved only when it is `false` (`notifyField`). `ROUTINE_DELIVERY` (`routine-delivery-v1`) is the name a phone asks about before it offers these. When a run completes, `Routines.deliver` takes the reply from the run's own chat and either adds it to the target chat as an unread message (`chatTarget`: the chosen chat, else the bot's latest chat that can take it, else a new one) or posts it to Today with the routine as its source, the first line as the title. A failure is written on the run (`Not delivered: …`) and doesn't fail it. `destinationNote` adds a line to the run's turn that says where the reply will go, so the bot writes for it. The `routine_create` and `routine_update` tools take `deliver` and `notify`, and a `to: "chat"` with no chat named goes to the chat the bot was asked in, when that chat can take a result. A chat that was sent a result keeps up to five of them in `chat.posted`, and `Workspace.send` puts them in front of that chat's next turn once and clears them, because the session behind the chat never saw a message that was written in the routine's chat. `desktop/notify.mjs` sends nothing for a run whose routine has `notify === false`, whether the run worked or failed, and opens `run.delivery.chatId` when the result went to another chat. The editor is in `src/Routines.tsx`.

**Keeping the work moving.** `desktop/keep-moving.mjs` holds the rules and `Workspace.keepMoving` (in `workspace.mjs`) runs them after a reply. While the turn's plan (the session's task list; Pi gets one from the `update_plan` tool, `desktop/providers/pi/plan.mjs`) has open steps, the bot gets another turn in the same session and run, at most 8 times and not when the same open steps come back. A reply that names its next step without doing it gets up to 2 more. Never past a question to the person, an open request, Stop, a message waiting in the queue, Plan mode, a routine or a Proactive run, a group chat or a failed turn. The run records `plan`, `continued` and `stoppedOpen`, and the window and phone say so ("↻ Kept going: N plan steps were open", "Stopped with N open steps" with Continue; `src/keep.ts`). A question unanswered for 10 minutes is detached (`desktop/interactions.mjs`): its tool call gets a plain "No answer yet" result, the card stays as waiting, and the answer is the person's next message, quoting it. Approvals keep waiting. Queued messages from one person are read in one turn (`takeBatch`), each still its own message in the chat.

**Reactions.** When a person reacts to a bot's message (the owner or a team member, in a chat with one bot), `desktop/reaction-turns.mjs` gives that bot a turn of its own after a few seconds, so reactions made together count once. The bot is told the emoji and the message, and how much of the chat model's plan is used where the provider reports it. It judges from what the reaction means in the conversation, not from the emoji: it may answer with nothing, a reaction of its own on the person's latest message (`react`), or a short reply, and a turn with no text ends with exactly `[SILENT]`. No emoji is named in what it is told. The turn adds no message from the person and stays hidden from the apps (no run, typing or streamed text) until its text can no longer be `[SILENT]`. A silent answer leaves no message, unread mark or notification. A message from the person ends a turn that hasn't replied, or replaces one not yet started. No turn starts while the chat is working, past 24 a day for each bot, or while the plan has a limit 90% or more used. Every bot is also told, in its instructions, to confirm how often a routine or panel refresh runs, where its result goes and whether it notifies before making one.

**Today items in a chat.** `desktop/mentions.mjs` knows a mention of kind `board` (`{ kind: "board", id }`), next to project, wiki and file. `resolve` finds the item in Today, refuses one that no longer exists, and gives the model its title, kind and category, who posted it and from which routine, its text, up to ten links and its id (for the board tools). It doesn't check the bot's access, because Today is the person's own. The message keeps a short copy (title, kind, up to 600 characters of text and its links), so `src/MentionMenu.tsx` can show the "From Today" card after the item itself is cleared. In `src/Board.tsx`, **Discuss** and **Let's do it** go through `startChat` in `src/app.tsx`, which attaches the item. `BOARD_MENTIONS` (`board-mentions-v1`) is the name a phone asks about first.

**Voice.** Everything that reaches a speech provider goes through the link's `Voice` (`desktop/link/voice.mjs`, described in `desktop/link/VOICE.md`), which `LinkHost` builds as `link.voice`, so the computer and its phones share one set of choices and keys. `desktop/voicedesk.mjs` shapes what the page needs from it as plain data that never holds a key: the settings, the lists of models and voices, a recording to text, text to audio (split at sentence ends, since a provider takes 4,000 characters at a time, with Markdown marks, code and link addresses left out), and a live session. A live session gets the bot's name and role as instructions and one tool, `ask_bot`; `liveTool` runs a call to it as a normal turn in the chat (`Workspace.send`), with the chat's own history, tools and approvals, and returns the reply cut to a length that suits speech. A turn can outlast its tool call: the bot stops to ask the person for an approval or an answer, or works for a long time (`handoffMs`, 45 seconds). The voice is not left silent: the call then answers at once with what is going on ("Pip needs your approval before it can go on: …"), the request is on screen in the chat where the person answers it (the voice can't answer it for them), and when the turn ends the voice is told the bot's reply (`say`: through Codex for a Codex session, this window's or a phone's; through the page for this window's other sessions). A voice that can't be told gets the reply with its next call, and a call made while such a turn is still under way never starts a second turn. `desktop/codexvoice.mjs` is `backend.voice.codex`: live voice on a ChatGPT sign-in, through an app-server of Codex of its own with the experimental API on (`thread/start`, `thread/realtime/start` over WebRTC, the tool call as `item/tool/call`, `thread/realtime/stop`). OpenAI documents none of that, so an update of Codex can break it. The helper is told whom a session is for (`chatId`, `botId`, `botName`, which the link passes for a phone's session too) and tells the voice desk before the voice can speak (`noteSession`), so a tool call from a phone's session runs in that phone's chat; such a session is not shown in this window and doesn't change its peer-to-peer rule. `voices()` asks Codex for its realtime voices, which are not the ones in its published types. The page's side is `src/voice.ts` (recording, playback and one client per kind of live session: WebRTC, and a socket each for OpenAI, Gemini and ElevenLabs, with microphone sound captured by `public/pcm-capture.js`), `src/VoiceSettings.tsx`, `src/ComposerVoice.tsx` and `src/LiveVoice.tsx`. The window may use the microphone for sound only and only in the app's own page (`setPermissionRequestHandler` in `desktop/main.mjs`), talks peer to peer only while a WebRTC session is open, and its Content-Security-Policy allows sockets to the three providers' addresses and nowhere else. `test/voicedesk.test.mjs` and `test/voice-smoke.mjs` use stand-ins; no test in `npm test` calls a speech provider. `test/voice-live.mjs` is the check with real speech, on this computer's own ChatGPT sign-in and not part of `npm test`: sentences made with macOS's `say` are played into a stand-in microphone (the app is muted), in the desktop window and through the link as a paired phone does it, and it shows the voice speaking as the chat's bot, a spoken request run as a normal turn in that chat with the answer spoken, the bot stopping for an approval with the voice saying so and going on once it is answered, and the session ending on both sides.

**iMessage and Mail.** `desktop/mactools.mjs` makes the tools and `desktop/mactools-mail.mjs` holds the Mail scripts. The choice is `settings.macTools` (`{ imessage, mail }`, each `off`, `read` or `interact`, and `off` unless it holds a known level). `set`, `status` and `grant` are calls only this window makes: they are not in `REMOTE_METHODS`, and `changeSettings` refuses the setting too, so a phone and a bot can't change it. Every tool call checks the level again (`allow`), so a session that started earlier can't outlive a change, and a change reopens the open sessions. On a platform that isn't macOS no tool exists and a level above Off can't be set. iMessage runs the `imsg` program with an argument array and never through a shell (`imsg chats`, `history`, `search` and `send`, with `--json`); Mail runs `/usr/bin/osascript` with fixed JavaScript for Automation scripts, and a bot's values reach a script as one JSON argument that has already been checked, never as script text. An answer is bounded (a text at 2,000 characters, an answer at 40,000, and a limit on each list and on how many results a call may ask for) and says when it cut something. A send or change goes through the approval flow (`skipPermission: false`) and counts toward five a reply, and the tools that send or change aren't offered to a turn nobody watches. A refusal is a sentence a bot can act on (the program isn't installed, a permission is missing, Mail isn't running or is showing a dialog). Whether macOS has allowed a tool is found without using it: Full Disk Access by trying to open the Messages database (and reading nothing), and Automation by asking the app a harmless question, without starting an app that isn't running unless the person chose **Grant**. `IMSG_INSTALL` holds the install command the page shows, and `src/MacTools.tsx` is the page.

Nothing here has been run against real messages or mail. `test/mactools.test.mjs` uses a fake `imsg` (`test/fixtures/fake-imsg.mjs`) and a fake script runner, and `node:vm` only checks that the Mail scripts parse. So the scripts' calls into Mail have never been run against Mail, and `imsg` has never been run by Botkins at all. If the real program's output differs from the stand-in's, the tools say that `imsg` answered in a form Botkins doesn't understand and suggest updating it.

**Html blocks.** `desktop/frames.mjs` keeps the page of an html block as a file and serves it at `<APP_SCHEME>://frame-<id>/` (the app's own scheme, `APP_SCHEME` in `desktop/app-window.mjs`) with its own content security policy (no network, scripts only, sandboxed). The app draws it in `<iframe sandbox="allow-scripts">`; a bridge script gives the page `window.botkins` (`getData`, `sendAnswer`, `openLink`, theme) over `postMessage`. The earlier bridge names, including `window.bighelp`, are the same bridge, so pages written for them still run. The main process also cancels any request a frame makes that isn't its own page, and any navigation of a frame. A policy has no word for peer-to-peer connections, so `desktop/view-guard.mjs` runs first in every page a bot wrote: it removes the ways to open one (`RTCPeerConnection` and its relatives, `WebTransport`) and takes every nested frame out of the page the moment it is put in, since a frame would be a window with all of that back in it. A bot's HTML app in its own window gets the same guard, and its session has a proxy that is not there, so no connection leaves it whatever its page does. **Custom views on a phone.** The link is given `backend.frames` (`desktop/main.mjs`): `page(id)` hands a paired phone the page as the bot wrote it and its data, and `chatFor(id)` names the chat an answer from a view in a Today panel goes to, so the phone can draw the view in a sandbox of its own with the same rules (no network, an answer only into the message box, a link asks first). If `FRAME_CSP`, the bridge's API or the size limits here change, the phone's copy has to follow.

**A tool that refuses.** Botkins' own tools refuse with a sentence that says what to do instead ("Create at most ten tasks per reply."). The other runtimes' tool server passes that sentence on. The Copilot runtime told the model only "Tool execution failed" for a tool that threw, so a bot could not learn the rule and took the app for broken. The adapter now hands every tool to the runtime wrapped (`spoken` in `desktop/providers/copilot/index.mjs`): a failure becomes a result that says it failed and carries the tool's own words. Checked with a real model: asked to change a task that doesn't exist, the bot answered "This task no longer exists."

**Model providers.** Everything Botkins needs from a model backend goes through the contract in `desktop/providers/provider.mjs`: a status (installed, signed in, which account and plan), sign-in and sign-out, a model list, and sessions that take a message and emit events. `desktop/providers/index.mjs` is the registry, and a model selection names its provider. Each provider is one folder, and only that folder may import the backend's SDK. Botkins' own features (tools, memory, Teamwork, mentions, skills and MCP settings, approvals) are provider-neutral, so adding a provider means adding a folder, listing it in `desktop/main.mjs` and giving it a mark in `src/ProviderIcon.tsx`. A chat whose model moves to another provider starts a session there and takes its transcript along.

- The registry keeps which providers the person switched on (`settings.providers`; OpenCode and the ACP agents are off until added), and remembers each provider's status for half a minute and its models for a minute. A provider that is slow to start is reported as starting and left out of the model list until it answers; a provider that fails never hides the others. `State.providers.revision` goes up when the page should ask again.
- When the provider behind the global default model is switched off or signed out, the default moves to the recommended model of a provider that can answer. A provider that is only slow or failing is left alone.
- A new workspace has no default model until a provider is connected (`settings.modelUnset`, `firstDefaultModel` in `desktop/workspace.mjs`): then it is that provider's recommended model. With several connected at once, the first by name decides, alphabetically, and one that is still starting and comes earlier in the alphabet is waited for. A workspace that already exists keeps its default.
- No provider stores a credential in Botkins. Each backend's own tool keeps its sign-in, and Botkins asks the tool who is signed in.

The providers built on a command-line tool share four modules:

- `desktop/providers/cli.mjs` finds a tool (the app's PATH, the login shell's PATH, then the usual install folders, because an app opened from the Dock has a short PATH) and talks JSON-RPC over a child process's input and output.
- `desktop/providers/toolbridge.mjs` offers Botkins' own tools to a backend as an MCP server. It listens on 127.0.0.1 only, each session has its own address and secret, a request that names a browser origin is refused, and a session's tools are only behind its address while its turn runs. A conversation keeps the same address from turn to turn, because a backend that keeps the conversation loaded goes on using the address it was given first.
- `desktop/providers/commands.mjs` is the "/" menu for backends without a command surface of their own, and `desktop/providers/skills.mjs` gives them Botkins' skills: the bot's instructions list its skills, and a `skill_read` tool returns one when the bot is about to use it. The skills inside plugins are listed too.
- `desktop/providers/sessions.mjs` remembers which backend conversation belongs to which Botkins session. A conversation the backend has lost continues from Botkins' own transcript.

**ChatGPT** (`desktop/providers/codex/`) is the provider's own harness, used when Settings → General → Harness is Provider default (see **Harness** below). It runs `codex app-server` and speaks its JSON-RPC protocol. Sign-in is Codex's own "Sign in with ChatGPT" (`account/login/start`), the model list and thinking levels come from `model/list`, and a Botkins session is a Codex thread. Approval levels map to Codex's approval policy and sandbox, and Codex's requests (a command, a file change, more access, a question) go through the same approval rules as Copilot's. A thread stays loaded for half an hour after its last turn (six at most), so a follow-up starts at once; a thread whose instructions or MCP servers changed is unloaded first, because a loaded thread keeps the settings it was loaded with. Codex uses the person's own Codex home, so MCP servers in their Codex configuration are loaded too.

**Claude** (`desktop/providers/claude/`) is the provider's own harness, used when Settings → General → Harness is Provider default. It is on the Claude Agent SDK (`@anthropic-ai/claude-agent-sdk`), which drives Claude Code: the copy the person installed, else the one that ships with the SDK. Sign-in is `claude auth login`, and the models come from Claude Code itself, asked with a prompt that never sends a message. Each turn runs Claude Code with Botkins' instructions appended to its own system prompt and the approval level as a permission mode. No Claude Code settings file is loaded: not the person's own (nor their skills or cloud connectors), and not a project folder's, whose permission rules and hooks could otherwise approve or run things without asking. In a coding chat Botkins reads the folder's `CLAUDE.md` (or `AGENTS.md`) itself and passes it along. MCP server addresses and their secrets go to Claude Code over its input, not on its command line; a Claude Code older than the SDK expects can only take them as arguments, and when the SDK's own copy is present that copy is used instead. Anthropic's terms decide who may offer a Claude plan sign-in in a product; check them before distributing a build with this provider on.

**OpenCode** (`desktop/providers/opencode/`) starts `opencode serve` on this computer and uses its HTTP API and event stream. OpenCode holds the person's model services; Settings connects one through OpenCode's own integration calls (an API key or a sign-in page). OpenCode keeps MCP servers per folder, so each session's bridge has a name of its own and the session's rules allow that one and no other session's. It uses the person's own OpenCode configuration.

**ACP agents** (`desktop/providers/acp/`) are one adapter for any agent that speaks the Agent Client Protocol; `agents.mjs` lists the ones offered, with the commands T3 Code uses for them. ACP has no system prompt, so a bot's instructions go ahead of the first message of a session and again when they change. A tool call is treated as one of Botkins' own (and so never asks) only when it is not one of the agent's built-in kinds and names exactly a tool this session offers; a call's title alone is never trusted, because the model writes it. The adapter is checked against the Copilot CLI's ACP mode; the listed agents themselves were not installed where it was written.

**GitHub Copilot** (`desktop/providers/copilot/`) is registered first, which makes it the provider of a model choice saved without one (choices from before there were several providers are such choices). That is all "default provider" means: nothing steers a person to it. It is on the Copilot SDK 2.0 (`@microsoft/copilot-sdk`):

- On a Mac the runtime runs as its own program, the one GitHub signs and ships in the SDK, and never inside Botkins' process. The reason is the keychain. A person's Copilot sign-in sits in keychain entries named "copilot-cli" that every Copilot program on the Mac shares, and macOS lets an entry be used without asking only by programs it lists by who signed them. Loaded inside Botkins, the runtime read and saved that sign-in as "Botkins": each save left only Botkins' mark on the entry, the person's other Copilot programs were locked out and macOS asked them for access ("copilot wants to access key “copilot-cli” in your keychain"), again after every save, whatever the person had answered. Run as GitHub's own program it is Copilot to the keychain, like the person's Copilot CLI, and Botkins never touches the entry. On a Mac nothing falls back to the in-process runtime; a runtime that can't start is an error. On Windows and Linux, where there is no such list, the runtime runs inside Botkins' process, with a child process as the fallback. `BOTKINS_COPILOT_RUNTIME=stdio` or `=inprocess` chooses one for a trial.
- A trial run never uses the keychain sign-in. Its runtime is handed a token (`BOTKINS_COPILOT_TOKEN`, else the one `gh auth token` gives) or runs signed out, so a test can't put a keychain question on anyone's screen or change the entry. `BOTKINS_COPILOT_SIGNIN=keychain` asks for the saved sign-in, for a deliberate check.
- Botkins keeps its own Copilot state in `<data>/copilot`, apart from `~/.copilot`. Sessions therefore open without loading the global MCP servers, plugins and session history of Copilot CLI. Conversations from earlier versions are copied over on first start.
- Each conversation is a durable Copilot session. After a reply the session stays open (for half an hour after its last use, up to eight at a time), and opening a chat readies its session, so a follow-up starts in about a second. Sessions are closed as rarely as possible: in this runtime a session that starts soon after another one closed can wait seconds for its tools, so a model or approval change is applied to the open session, and the "/" menu of a new chat uses one kept-open session per bot.
- `desktop/providers/copilot/agents.mjs` reads the person's custom agents from `<Copilot home>/agents` (`*.agent.md`: YAML front matter and a prompt). A provider offers such agents through `agents()` in the contract, and `desktop/agents.mjs` turns the chosen ones into bots.
- Each session gets only what Botkins names: its tools, the skills and MCP servers from Settings, and the runtime's built-in tools except its workflow tools. The runtime's own GitHub MCP server and its pull-request skills (outside project folders) are off.
- `BOTKINS_TIMING=1` prints how long each runtime step took. `BOTKINS_COPILOT_LOG=debug` sets the runtime's log level.

**Model details.** Every entry of the model catalog can carry what is known about the model: `contextWindow`, `maxPrompt` (the most a request may hold, where the provider names a limit below the window), `maxOutput`, `vision`, `tools`, `effortNotes` (the provider's own line for each thinking level), `description`, `knowledge`, `vendor` and `tier`. The rule in `desktop/modeldetails.mjs` is that every value comes from the provider that serves the model, and a value nobody stated is left out. Nothing there is a default, because a wrong number is shown as a fact and is what the context meter counts to. `modelDetails()` drops anything that isn't a real value (a count that isn't a whole number above zero, empty text), and each adapter's `models()` fills it from its own source:

- GitHub Copilot: GitHub's model listing (the three limits, vision, tool calls, the maker and the price category).
- ChatGPT: Codex's own line about the model, whether it takes pictures, and each thinking level's line. The window comes from Codex's catalog file (`models_cache.json` in the Codex home), where `maxPrompt` is the part of the window Codex fills before it makes room, else from the window Codex reported after a turn on the model.
- Claude: Claude Code's own line about the model. The limits are what Claude Code reported for the model on this person's plan after a turn (its window and longest reply). Until it has, they are the table Anthropic publishes (`PUBLISHED` in `desktop/modeldetails.mjs`: window, longest reply and, for current models, the knowledge cut-off, pictures and tools). A model that isn't in the table gets nothing from it.
- OpenCode: its listing's limits (window, input and output) and what the model takes.
- ACP agents: the agent's own line, and the window the agent reported after a turn.

**Another computer's Botkins.** `desktop/remotehosts.mjs` makes this app a client of another computer's link host, like a paired phone but of kind `"desktop"` (the contract is `desktop/link/CONTRACT.md`). The client library is the phone app's `src/link/`, copied unedited into `desktop/remote/client/` and compiled with its crypto packages into `desktop/remote/link-client.mjs` by `node scripts/build-link-client.mjs`. Both the generator and the tests check the release-approved hashes in `desktop/remote/client-sources.json`. For an approved phone update, record the new hashes and pass the phone repository path to the generator. Each host's credential is wrapped by the system keychain's key in the installed app (as the vault's is) and kept in `remote-hosts.json`, beside the id of the host in use; a trial run keeps it in its own folder. `resume()` goes back to that host when the app starts. While a host is in use, `appSnapshot()` is that host's state rebuilt from the link's parts (`snapshotOf`: chats are listed, and the chat on screen is followed for its messages and running turn), every call the window makes is sent to the host when the link allows a client to make it (`REMOTE_METHODS`) and refused in words otherwise, and the window's own look (`appearance`, `sidebar`) stays this computer's. `state.remote` says which computer is shown. The window's parts are `src/RemoteHosts.tsx`: the switcher, the line across the top, the main window's state while the computer in use has sent nothing (it can't be reached, a different computer answered, or it no longer knows this one: **Use this computer instead** and **Try again**, which is `useRemoteHost` with the same id), the pairing and team join forms, and Settings → Computers and teams. The first launch asks how Botkins is used here (`src/SetupChoice.tsx`): set up on this computer (the welcome, then the first bot), connect to another computer, or join a team. The first bot step is never shown while another computer is in use.

**The side pane, opened by a bot.** `desktop/sidepane.mjs` keeps a chat's panels on `chat.pane` and gives a bot `side_pane_show`, `side_pane_web`, `side_pane_update`, `side_pane_close` and `side_pane_list` in a turn the person is there for. The contract for every client is `docs/SIDE_PANE.md`. Only `side_pane_web` goes through the chat's approval, because it makes the app request an address the bot chose; its address is checked first (http or https, no sign-in in it, nothing on the local network, a name looked up before it is trusted). The website viewer is an Electron `<webview>` whose guest is decided in the main process by `desktop/webviewer.mjs`: only the viewer's in-memory partition and an http(s) address may attach, with no preload, a sandbox, no new windows, no downloads and no permissions, whatever the page asked for.

**Files and folders for a window without dialogs.** A paired phone, or another computer using this one, can't show this computer's save, open or folder dialogs, so the same things exist as calls that answer or take the file itself (`desktop/phonefiles.mjs`, capability `files-v1`): `exportTemplateText` and `importTemplateText`, `exportUsageText`, and `exportWikiFile` in the desktop's three formats (`{ name, text }` for a web page, `{ name, base64 }` for a zip or a PDF, 4 MB at most). For a web page or a PDF the main process lays the document out itself with the window's own code, compiled for it by `node scripts/build-wiki-export.mjs` into `desktop/generated/wiki-export-doc.mjs`; a test fails when the window's sources have changed since. Folders are picked through a browser of the computer's own (`desktop/folders.mjs`, capability `folders-v1`): `listFolders(path?)` answers folder names only, inside the home folder or on a plugged-in disk (listed as `roots`), never a hidden folder, never a file, a few hundred names at most, and `addProjectFolder(path)` and `addSkillFolderAt(path)` take only a folder that browser could have shown. A project's folder sent by a paired device through `createProject` or `updateProject` passes the same check (`deviceArgs`); the window's own dialogs are not limited by it. A trial run browses a folder of its own (`BOTKINS_FOLDERS_HOME`), never the person's.

**Plans and limits.** `desktop/providerusage.mjs` reads each connected provider's plan and what is left of its limits, and answers the window and a paired phone with one shape (the call `providerUsage`, written down in `docs/PROVIDER_USAGE.md`). Each adapter reads its own provider in `usage()`: Claude through Claude Code's `get_usage` (started without a prompt, so nothing is used from the plan), ChatGPT through the Codex app server's `account/rateLimits/read`, GitHub Copilot through the runtime's `account.getQuota` and the signed-in account's plan. A provider that has no way to say returns null and is shown as not available. `ProviderUsage` keeps the last answers in `provider-usage.json` (with no account name in it), answers from them, reads a provider again in the background when its answer is older than two minutes, and never more than once in ten seconds. Nothing in it is a default: a value the provider didn't state is left out.

What a tool reports after a turn is kept by `ReportedLimits` in a file, `model-limits.json`, so it is known at the next start. Without a file (a test, a trial run) it is kept for the run. `Providers.known(selection)` gives the catalog's last entry for a selection's model without asking again. `Workspace.metered` uses it on every context report of a turn: the report's limit becomes `meterLimit(model)` (the catalog's `maxPrompt`, else its `contextWindow`), whichever harness runs the chat, because each harness reports a limit of its own and they differ for the same model. The harness's number stays only for a model whose provider states none, and the reports of a sub-agent a model started are left alone. The page shows the details in three places: `modelFacts` in `src/providers.ts` builds the short facts, which `src/ModelPicker.tsx` lists under each model (with the exact value on hover), and `src/ContextDetails.tsx` shows the window, the request limit, the longest reply and what the model takes for the model the chat last ran on, beside the chat's own token use.

**Harness.** `desktop/harness/` decides what runs a bot's turn. `settings.harness` is `copilot` ("Copilot SDK", the usual choice), `provider` ("Provider default"), `pi` ("Pi") or `omp` ("OMP"); anything else counts as `copilot` (`harnessField`). With Copilot SDK the Copilot runtime runs every chat, so skills, tools, MCP servers and their sign-ins, plugins and approvals are carried by one program. The Pi-compatible adapters in `desktop/providers/pi/` and `desktop/providers/omp/` share the same Botkins gateway and tool bridge for every provider's chats: ChatGPT and Claude plans, GitHub Copilot (`/copilot`, signed with headers a Copilot runtime of Botkins' own lends from its model requests, `desktop/providers/copilot/relay.mjs`, so Botkins never reads the keychain), OpenCode (`/opencode`, one model step of an OpenCode session that can only list the harness's tools, `desktop/harness/opencode.mjs`) and the key providers. Pi runs as `pi --mode rpc` with the extension registering its MCP servers. OMP runs as `omp --mode rpc-ui`, uses its own generated session id and `--resume`, and receives a 0600 per-session `mcp.json`, a disabled-project-MCP config overlay and the same Botkins extension without MCP registration. Both start from an isolated Botkins-owned agent folder, leave personal Pi/OMP setup alone and route approvals back through Botkins. The programs are registered as harnesses, not model providers: `Providers.list` and Settings › Model providers leave them out, while `harnesses()` reports installation for desktop, CLI and phone settings. The ACP agents are whole agents with no model endpoint, so they run themselves. A chat keeps its conversation when the choice changes: its next reply starts on the other harness from Botkins' transcript. Models are shown by name through `desktop/modelnames.mjs`, so no id reaches the page or phone.

- `index.mjs` decides who runs a model selection and gives the Copilot runtime the connections and models for a ChatGPT plan and a Claude plan. It tells the runtime each plan model's limits (`planModel`), because a runtime that isn't told assumes 128,000 tokens of prompt and 8,192 of reply (measured, runtime 2.0.1), about a sixth of what a current model holds. It is given what the model's provider states (see **Model details**): the window, the longest reply, the prompt limit (else the window less the reply room, else the window), and pictures, tools and whether it has thinking levels. A value the provider doesn't state is left out, never made up.
- `gateway.mjs` is a server on 127.0.0.1 that answers only to a secret made for this run of the app. The Copilot runtime sends its model requests there, and neither plan's sign-in passes through the runtime. It also keeps the waiting runs of Claude Code (see **A Claude plan's waiting runs**) and starts them when a chat on a Claude model opens (`warm`).
- `chatgpt.mjs` sends an OpenAI Responses request to the ChatGPT plan with the sign-in Codex keeps. It moves the system prompt into `instructions` and fills the reply's items into the last event, and requests name themselves "botkins". The endpoint wants instructions on every request, so a request with none is refused (`planRequest`) rather than given words nobody wrote. Botkins sends these requests to the endpoint Codex uses, with the person's Codex sign-in. This depends on OpenAI continuing to allow it.
- `claude.mjs` answers an Anthropic Messages request with a run of the official Claude Code program, unmodified and with its own sign-in, which Botkins never reads. The run is one that was started ahead of time and waits (see **A Claude plan's waiting runs**). Claude Code's own tools, skills, settings, memory and compaction are off. The Copilot runtime's tools are only listed to it, through a local tool server that refuses every call. It takes one model turn, and its stream events go back to the runtime, which runs the tools with Botkins' approvals. This follows NousResearch's claude-subscription-directsdk plugin for Hermes. Claude Code names its caller on every request, and a plan's five-hour window is metered by that name. Both the direct Agent SDK and the Copilot harness identify their Claude processes with `CLAUDE_CODE_ENTRYPOINT=botkins`. The release check `node test/claude-entrypoint-live.mjs /path/to/claude` verifies that label on both routes against a loopback model endpoint. Anthropic controls subscription metering. [T3 Code's metering investigation](https://github.com/pingdotgg/t3code/issues/24649).

**A Claude plan's waiting runs.** A run of Claude Code that is started for a request begins slowly and, worse, can stop in the middle of the reply: a person saw the first few words, a pause of seconds, then the rest at once. The cause is in Claude Code's own startup. Soon after it starts it checks whether the system tells it of changed files; on a busy Mac the system doesn't answer in time, Claude Code switches to looking by itself, and while it switches nothing it has read from the model gets out. Its own log says so (`[event-loop-stall] blocked for …ms` next to `[fs.watch probe] verdict: silent`): measured with Claude Code 2.1.325, a block of 1 to 13 seconds that begins anywhere from 2 to 8 seconds after the start, longer the busier the computer. No setting of Claude Code's turns that check off. So `ClaudePool` in `desktop/harness/claude.mjs` starts runs ahead of time, and a request is handed to one whose startup is over.

- **Handing over.** A waiting run is started with no request in it. `handOver` tells it the request over Claude Code's own control messages, the ones its SDK sends: the system prompt, the tool server, the extra request fields (`extraBody`: thinking, the thinking level, the longest reply, stop sequences and each tool with its whole description and schema) and the model. A tool's name for Claude Code is shortened when it is long (`toolNames`). A run that was started for a request instead takes the thinking level from its environment (`thinkingLevel`), because with the `--effort` flag Claude Code gives the whole reply in one piece at the end.
- **How many, and for how long.** Two runs wait, so that after one is taken for a request the other has finished starting when the next request follows at once (the Copilot runtime's request after a tool call). A run is handed a request only once its startup is over, which is read from the run's own log (`startedUp`: the log says when Claude Code has switched to looking by itself, or that it never had to; a run whose log says neither is taken to have started after 20 seconds). The log names the account and folders, so it is kept in a folder only the person can read and removed when the run ends. The waiting runs are ended after ten minutes without a Claude request, and whenever the program, its folder or its sign-in environment changes. Each run serves one request and is then ended, and taking one starts another in its place.
- **Told ahead, inside a turn** (`tellAhead`, 2026-11-23). A tool-calling turn makes one request per tool round, and each extends the one before it. While one request is answered, a waiting run is told the same control messages and every turn of that conversation so far, so when the next request comes it is handed only its new turns. A run is taken only when the system prompt, model, effort, reply room, tools and every earlier turn match exactly (`outline`, a chain of digests), so no other request is ever handed to it. Measured with Claude Code 2.1.325 against a loopback model endpoint: a request after the second reaches the model in 35 to 60 ms instead of 110 to 490 ms (the old cost grew by about 4 ms per earlier turn, replayed one at a time). It uses one of the waiting runs, not another process; one that refuses or times out falls back to a run of its own, as below, and telling ahead then pauses for a minute. `pool.counts` says how requests were served (`ahead`, `handed`, `own`).
- **What a waiting run costs.** Nothing of the person's Claude plan, because it makes no model request until it is given one. It does hold memory, about 165 MB each (measured). That is why there are only two, and why they end when nobody is using Claude.
- **When they start.** When a chat on a Claude model opens (`warm` in `desktop/harness/gateway.mjs`, called from `Harness.session`) and whenever a request takes one. A request never waits out a whole startup: when no run is ready within a second and a half, the request gets a run of its own, as it would without the pool (`takeReady`). That reply begins as soon as it can and may be stopped in the middle by that run's startup, which is the old behaviour. So the pause is gone whenever a run is ready (a message sent a while after its chat was opened, and most requests of a turn) and can still happen when none is (a message sent within seconds of opening a chat, or several requests in quick succession, on a busy Mac).
- **Measured** on a Mac under heavy load (load average 20 to 40), through the gateway, twelve replies handed to ready runs: text began 0.9 to 3.6 seconds after the request in eleven of them and no piece waited more than 0.35 seconds. With a run started for the request, in the same hour: pieces waited up to 5.6 seconds, and several replies arrived whole after 16 to 25 seconds.
- **When it doesn't work.** A run that refuses a part of the request or doesn't answer within 15 seconds is ended, and a run is started for that request as it was before. Measured this way, a reply begins about a second sooner and no piece waits more than a third of a second. A `Gateway` with `waiting: 0` keeps none waiting.

**Streaming text.** A reply's live text is built by `appendStream` in `desktop/workspace.mjs`. A turn can hold several messages (a line before a tool call, another after it). The Copilot runtime sends each message's pieces under that message's id with nothing between two messages, so without a break they read as one sentence ("…today's calendar.Two calendars had more…"). The first piece of a new message therefore starts a new paragraph, and a message that begins with nothing waits for its first words before the break is made. The other providers' adapters put the break in themselves and send no id.

With Provider default, the command-line providers have the same reach as far as they can. They get an MCP server's sign-in token when a session opens (`serversWithTokens` in `desktop/providers/sessions.mjs`), Botkins' skills through the `skill_read` tool, and the skills inside plugins. Plugins as a whole, and questions on ACP agents, are still only on the Copilot runtime.

**Upgrading from an earlier build.** `desktop/home.mjs`, `desktop/keychain.mjs` and `desktop/start.mjs` carry the rename, and `test/rename.test.mjs` checks it in temporary folders with stand-in keychains.

- **The data folder.** `adoptFolder` in `desktop/home.mjs` renames the earlier build's data folder, when it holds a workspace, to "Botkins", once, in one step with nothing copied, and leaves a link under the old name pointing at it (a junction on Windows). The link keeps paths saved under the old name working. `desktop/main.mjs` calls it first, in the installed app only and never when `BOTKINS_DATA_DIR` is set. It does nothing while another copy of the app is running on the folder (Chromium's `SingletonLock` names the process), or when a "Botkins" folder with anything in it exists (an empty one is removed first). The app then goes on using the folder where it is. `dataHome` picks the folder: the one named by `BOTKINS_DATA_DIR` (tests and smokes use it), else the "Botkins" folder in the application data folder once it holds a workspace, else the earlier build's folder if it holds one, else a new "Botkins" folder. A bot works in `<folder>/data/files/<bot>`, which no longer has the old name in it. Claude Code and OpenCode find a conversation again by the folder it was started in, so a chat they ran continues from Botkins' own copy of the conversation. The wiki, the vault, each provider's sessions and the paired phones (`link/link.json`) move with the folder. `test/folder-move-live.mjs` checks that a Copilot chat goes on after the rename.
- **Environment variables.** `env("NAME")` in `desktop/home.mjs` reads `BOTKINS_NAME` first, then the earlier spelling of the same name.
- **The keychain.** On a Mac, Electron's `safeStorage` keeps its secret in a keychain entry named after the app: the earlier build's "Safe Storage" entry before the rename, "Botkins Safe Storage" after it. A process named Botkins can't open what the first entry wrapped. Two keys are wrapped that way: the vault's key (`<data>/vault.json`) and the phone link's private key (`<data>/link/link.json`). Windows keeps the secret in the data folder, under the person's own account, so nothing changes there. When the installed app finds a key it can't open and the Mac has the earlier entry, it starts itself once more as a helper (`desktop/start.mjs` decides this before anything else runs, because the helper must take the earlier name before Electron sets up). The helper opens no window and uses a throwaway folder. It reads the wrapped keys from its input, opens them, prints them to the app and exits. The app first says what is about to happen, then macOS asks the person whether Botkins may use the earlier build's entry, because the app's identity changed with its name. The app gives up on a helper that hasn't answered after three minutes and goes on with the keys locked. The vault then saves its key under the new entry as well, beside the earlier wrapping, which is never overwritten, so an earlier build still opens the same vault; if its own wrapping is ever lost, or an earlier build saves the vault, the helper runs once more and writes it again. The link's key is saved under the new entry in the same start, so the helper is needed once. A key counts as opened only when a 32-byte key comes out: the wrong entry sometimes turns a wrapping into junk instead of failing. A person who says no, or a helper that can't run, leaves every locked key untouched, and the app asks again at the next start. The helper is this app asked on its command line to decrypt with the earlier entry, so any program running as the same person could start it too; macOS still asks each time unless the person chose Always Allow, which is why the app asks for Allow. A development run keeps its keys in files and never asks.
- **Files and pages.** Template files read both formats, `botkins.bot-template` (written) and the earlier build's template format. The page bridge for html blocks and apps is `window.botkins`, with the earlier bridge names and `window.bighelp` as the same object.
- **Names kept on purpose.** The app's scheme for html blocks and apps (`APP_SCHEME` in `desktop/app-window.mjs`) keeps its earlier value, because their stored data is tied to it. The skill origin value for skills that come from the app keeps its earlier value too, because the phone link uses it. The tool server that the command-line providers see is now named `botkins` (`BRIDGE` in each provider), and bots are no longer told to use a tool by one program's name when they ask the person a question.

The Today implementation draws on the Bighelp Spaces and panel model at `f6aa0ab`. The look comes from the Botkins design kit in `design/botkins-kit`, the same kit the phone app uses: its characters, palettes, motion, fonts and color tokens.
