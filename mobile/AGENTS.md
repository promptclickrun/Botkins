# Botkins

Botkins is the phone app for the Botkins app on the person's computer (the desktop app, in `../desktop`; it was renamed during development, so a few code names and paths still use the earlier name, and the phone's code says `desktop/` for it). A phone pairs with a computer (or with several, using one at a time), then chats with the person's bots and manages everything about them: bots, chats, routines, tasks, tools (MCP servers), skills, model providers, credentials, the wiki and settings. It can also show the computer's screen, tell the person when a bot needs them, let bots use the phone's calendar, contacts and more, and talk with a bot out loud. The Marketplace connects apps through the person's own Composio account.

## Stack and commands

- Expo SDK 58, React Native 0.88 (New Architecture), React 19 with the React Compiler, TypeScript strict, Expo Router with typed routes.
- Expo changes between SDKs. Before you use an Expo or React Native API, read its types in `node_modules` or the versioned docs at `https://docs.expo.dev/versions/v58.0.0/`. Do not trust memory.
- Install packages with `npx expo install <package>`. A package with native code needs a new native build, so ask before you add one.

The relay ships apart: `cd relay && npm test && npm run deploy` (it serves `relay.botkins.app`). Before an upload, run the release build once in a simulator (`xcodebuild … -configuration Release -sdk iphonesimulator`, then install it): it has no Metro, so it shows what a tester gets. Upload only when the person asks.

- **Android testers.** Set `FIREBASE_APP_ID` and `FIREBASE_PROJECT` in your shell. Run `BOTKINS_BUILD=<n> sh scripts/android-testers.sh "notes"` to send a signed APK to the Firebase `testers` group. Use the Firebase console to invite testers.
- **Android on Play.** `BOTKINS_BUILD=<n> sh scripts/android-play.sh` (see its header) typechecks, tests, prebuilds and builds a signed App Bundle for Google Play's internal testing track. The upload key is `~/.botkins-keys/botkins-upload.jks`, its password in the Keychain item "Botkins Android upload key"; `plugins/withAndroidRelease.js` reads them from the environment, so neither lands in `android/`.
- **Five things are signed.** The iPhone app, embedded Watch app and the three extensions in `targets/` (`widgets`, `notify`, `notify-ui`) each have a bundle id and a provisioning profile, and `scripts/ExportOptions.plist` names all five. A new target or profile goes there too. The app and `widgets` share the App Group `group.app.botkins.mobile` (the widgets' snapshot): the capability must be on both identifiers, and their profiles remade after it is added.
- **`BOTKINS_BUILD` also picks Apple's notification service.** `app.config.ts` sets `expo-notifications` to `production` only when `BOTKINS_BUILD` is set, and `scripts/testflight.sh` requires it. So make a TestFlight build with `BOTKINS_BUILD` set, so it uses Apple's production service. A build made without it uses the development service. The phone reads which one it got and tells the computer (`env` in `link.push.register`).
- **Native pieces.** `app.config.ts` lists the native packages and plugins: the device tools' (calendar, contacts, location, media library, mail composer, HealthKit), voice's (`expo-audio`, `expo-speech-recognition`, WebRTC), notifications and the Apple targets (`@bacons/apple-targets`). Local Expo modules add MusicKit and the WatchConnectivity bridge. `react-native-webview` draws custom views, and `expo-glass-effect` with `expo-blur` the glass of floating controls; they need no plugin. `ios.appleTeamId` and the keychain group (`BotkinsKeychainGroup`) are there too. A change to any of these needs `npx expo prebuild` and a native build.
- **Time Sensitive Notifications** is not on yet. The note in `app.config.ts` says how to turn it on (a switch in the Apple developer account, a new profile, one entitlement). The computer already marks requests that way; until then they arrive as ordinary notifications.
- **Notifications on the relay** need the Worker's APNs secrets (`relay/README.md`, "Push notifications"). Without them the push route answers 503 and no notification is sent. The keys must be Botkins' own: Apple makes a push key for chosen apps and for one environment or both, so the relay holds one for production (TestFlight and the App Store) and one for the sandbox (a development build on a real phone). Another app's key answers `TopicDisallowed`.

One simulator and one Metro are shared. Only the lead session runs the app, builds it and takes screenshots. Other sessions run `npx tsc --noEmit` and `npm test` only.

On this machine Metro's file watcher misses edits (there is no watchman). It missed every edit in one long session. Restart Metro (`npx expo start`) and relaunch the app after your edits, before you judge what the app shows or debug the code. The debugger's first target can be another simulator that is connected to the same Metro, so check which device you are looking at.

**What a simulator can't check.** In a simulator the phone could not get a real notification address from Apple, and the notification extension did not run for a notification delivered locally (scheduled on the phone). So sealed alerts, Live Activities started or changed by a push and a push through the relay need a real phone. The phone's speech recognizer does not run in a simulator either, so dictation and talking by turns stop there with "Dictation stopped". A screenshot from `agent-device` leaves the Dynamic Island out; `device_screenshot` shows it.

## How a screen talks to the computer

- **Read** state with the hooks in `@/state/hooks`: `useBots()`, `useBot(id)`, `useChats()`, `useChat(id)`, `usePart("tasks" | "panels" | "board" | "projects" | "mcp" | "settings" | "live" | "runs" | "meta" | "credentials" | "host" | "phones" | "asks" | "voice" | …)`, `useRoutines()`, `useModels()`, `useProviders()`, `useSkills()`, `useWatchedChat(chatId)`, `useBotActivity(botId)`, `useChatActivity(chatId)`. State arrives by itself after every change on the computer; never copy it into local state except as a form draft.
- **Change** things with `api` from `@/state/link`. It is typed by `Calls` in `src/link/types.ts`: `await api.updateBot(id, { name })`. Wrap a call in `attempt(...)` to show its failure as a toast: `const id = await attempt(api.addBot(bot), "Bot created")` resolves to `undefined` when it failed.
- After a call, do not update state by hand. The change comes back through the link in well under a second.
- Lists the computer is asked for (`useModels`, `useProviders`, `useSkills`) are `undefined` while loading. Call `refresh("skills")` after you change something behind one.
- The computer can be unreachable. `Page` shows a banner for that by itself. Disable an action with `useOnline()` only where a tap would be confusing.
- **Name a store like a hook.** A zustand store that a component calls must be named `use…` (`const useThing = create(…)`). The React Compiler knows a hook only by its name; a store named otherwise is skipped on some renders and the screen breaks with "Cannot read property 'length' of undefined".
- **Save the phone's own state with `keep.ts`** (`readKept`, `keep`, `forget`), never with `SecureStore` directly. It keeps a value readable while the phone is locked, because the app is started in the background for a notification, a Live Activity or a bot's question. A read that throws means the keychain can't be read yet, not that nothing was saved (`boot` in `link.ts` waits for it).

## Parity with the computer

A standing rule from the owner (2026-11-19): every setting and control the app on the computer has, the phone has too, at all times.

- When a setting or control is added or changed on the computer, add or change it on the phone in the same piece of work: the same choices, the same names, the same words. Tell the thread that owns the other app when a change starts here.
- The only exception is something that cannot work on a phone. Prove it with documentation (Apple's, Expo's, the provider's): put the link and the sentence that says so in "What the phone can't do" below. "Hard", "rare" and "not built yet" are not exceptions.
- A setting the phone can't change itself is still shown, with its value and one line that says where to change it.
- Most settings are fields of `Preferences` and are saved with `api.setPreferences({ … })`; the computer checks each one. A new field usually needs only the type in `src/link/types.ts`, a row or page in `src/features/settings/`, and the same field in `link-host/mock-backend.mjs`.
- **Where the pieces of the first full pass (2026-11-19) are**, so the next control lands beside its kind: the computer's own settings in `src/features/settings/` (`Desktop.tsx` Background and Storage, `ComputerAlerts.tsx`, `Access.tsx`, `Window.tsx` for its theme, font and side menu, with their plain logic in `computer.ts`); bots in `src/features/bots/` (`Access.tsx`, sections and filters in `src/features/home/arrange.ts`); chats in `src/features/chat/` (`Changes.tsx`, `ChatProject.tsx`, `side.ts` for `/btw`); Today, routines and projects in `src/features/today/` (`PanelRoutine.tsx`, `NewPanel.tsx`), `src/features/work/` (`Cadence.tsx` is the one schedule picker, `cron.ts` its math) and `src/features/projects/logic.ts`.
- Never put an `eslint-disable` for the hooks rules in a component: the React Compiler then skips that component.
- Before a release, compare the two apps: the computer's Settings pages (`../desktop/src`, start at its Settings navigation in `Settings.tsx`) and its per-bot, per-chat, routine, task, tool, skill and provider controls, against `src/features/` here.

### Not built yet (owed, not excused)

No documentation says a phone cannot do these, so they are not exceptions. Each needs a phone way of doing the same thing.

### Files and folders without a dialog

Where the app on the computer opens a file or folder dialog, the phone has its own way (built 2026-11-19; the desktop app has the calls from 0.15.2).

- **A file out** ("Export template…", "Export CSV", the wiki's "Export…"): the computer answers `{ name, text }`, or `{ name, base64 }` for a zip or a PDF, and `shareFrom` / `shareFile` in `src/state/files.ts` hand it to the phone's share sheet. The computer sends at most 4 MB in one piece and says so in a sentence.
- **A file in** ("Import…" for a template, tool servers "From a file…"): `pickTextFile` opens the Files app and reads the file as text (2 MB at most), and the text goes to the computer.
- **A folder** ("Add folder…", "Choose folder…", "Change folder…", "Add from folder…"): the sheet `/folders` (`src/features/folders/FolderPicker.tsx`; `use` is `project-new`, `project` with `id`, or `skills`) browses `listFolders` and makes the call itself. The computer names folders in the home folder and on plugged-in disks (`roots`), never a file, and checks a chosen folder again. Show its sentences as they come: a Mac can need one answer on its own screen before it lists Documents, Desktop, Downloads or a disk.
- **Capabilities.** `files-v1` (files out and in) and `folders-v1` (the folder browser) are named by the computer's app; `maintenance-v1` ("Clear cache", the computer's own "Send test") by the link. `useCapability(name)` in `@/state/hooks` reads one. Without it the control says "Update the app on your computer".
- **The plain logic** is in `src/state/fileText.ts` and `src/features/wiki/exporting.ts` (no React Native imports); `link-host/methods.mjs` (`fileArgs`) cuts each call to its shape before the computer's app sees it. `tests/computer-files.test.ts` checks all three and the demo computer's answers.

## Chat: composer, pickers, attachments and requests

All of this is in `src/features/chat/`.

- **The composer's row.** Attach on the left; on the right the model, shown only as its provider's mark (`ProviderIcon`), then the main button. There is one voice button and no separate microphone (the owner's rule). The main button is Stop while a turn is under way and nothing is written, Send as soon as there is text, a file or a pinned card, and otherwise the voice button (never in a group chat). When a live voice provider is chosen in Settings › Voice it starts Live voice in the chat (`openLiveVoice`; the voice dock then takes the message box's place, see "Voice"). Otherwise it talks by turns (`startTalk` in `src/features/voice/talk.ts`): the phone listens, sends what was said as a normal message, reads the reply aloud and listens again; `TalkBar` above the field says what it is doing, and the button ends the talk. Nothing with words goes in this row: the chat's header names the model. Above the field sit a Today card pinned by Discuss (it goes with the first message) and the chips. The box is drawn on `Glass` and floats over the chat; the attach button and the provider's mark sit on it bare.
- **The field grows with its text**, from one line to four (`MAX_LINES`), then scrolls inside. React Native 0.88 does not grow a field that keeps its own text, and reports its text's height only when its layout changes, so the height comes from a hidden copy of the text drawn at the field's width (the `Text` under the field in `Composer.tsx`). Keep that copy's type and width the same as the field's.
- **The field keeps its own text. Do not make it controlled again.** `Composer.tsx` never hands `value` back to the `TextInput` as a person types: writing text into an iPhone's field between keystrokes resets its autocorrect and inline predictions. The field is uncontrolled, and only text that comes from somewhere else (a picked suggestion, dictation, a draft put back after a failed send) is pushed in, once, with `setNativeProps`. Emptying the field uses `clear()`, which works whatever was pushed before. Read the comment above `shown` and `push` before you change anything that touches `value` or `onChangeText`.
- **Pickers.** `compose.ts` (no React Native imports, so `tests/chat.test.ts` runs it) exports `findTrigger(text, caret)`, which finds the `/`, `@` or `#` word that ends at the caret. `Suggestions.tsx` has a hook that loads each list and a function that turns it into `Option[]` for `SuggestionList`. `Composer.tsx` picks the list from the sigil:
  - `/` is `useCatalog` and `slashOptions`: commands and skills. `/model` and `/compact` run on the phone.
  - `#` is `useMentionables` and `recordOptions` (projects, with the chat's own first, then wiki pages, then files and artifacts), and after them `usePullRequests` and `pullOptions` (the chat's project's pull requests, read on the computer with the GitHub CLI; only with `prs-v1`).
  - `@` is `botOptions` and then `recordOptions` too, so either key finds everything. `botOptions` lists a group chat's members and "everyone", or in a chat with one bot the teammates it may ask (`teammates()` in `compose.ts`, empty when Teamwork is off).
  - To add a picker, add the sigil to `Sigil` and to the pattern in `findTrigger`, write the hook and the option function, and add a branch in `Composer.tsx`.
- **Mentions.** An option with a `mention` (a project, wiki page or file) becomes a `DraftMention`. It reads `#Label` in the text, also when it was picked with `@`: in a group chat `@name` addresses a bot, so a record never looks like one. It is sent in `SendOptions.mentions` as a `MentionInput` (at most `MAX_MENTIONS`). A mention whose `#Label` leaves the text is dropped. An option with `insert` puts text in the message: a bot as `@name`, a command, or a pull request as a Markdown link.
- **A Today card in a chat.** Discuss on a card (`discussBoardItem` in `open.ts`) starts a chat with the card's bot and pins the card above the field. The first message sends it: as a mention `{ kind: "board", id }` when the computer has `board-mentions-v1`, else as a quote at the top of the text (`withBoardQuote`). `splitBoardQuote` reads such a quote back out of a message, and `Messages.tsx` draws it as a card.
- **Attachments.** `uploads.ts` exports `upload(uri, name, onProgress, stopped)`, which sends a file to the computer in parts with `link.upload`, plus `MAX_FILES` and `MAX_BYTES`. The composer takes files from the photo library, the camera or the Files app, shows each with its progress, and sends the saved paths in `SendOptions.attachments`. It does not let a person send while a file is still going up.
- **Pull request links.** In project chats the owner's `#` picker inserts a Markdown link. A PR link in either person's messages opens the pane sheet with `pr-panel-v1`. Other links, older hosts and team members use the browser. The PR sheet reads one file's patch on tap. With `BOTKINS_DEV_PRS=1` the demo has a description, checks, review and changed file.
- **Capabilities.** The composer offers uploads only when `meta.capabilities` has `uploads-v1`, `#` pull requests only with `prs-v1`, a pinned card as a mention only with `board-mentions-v1`, and Live voice only with `voice-v1`.
- **Custom views (Rich UI).** A bot can put a page of its own (an html block) in a card or a Today panel. `HtmlFrame` (`src/ui`) draws it in a web view, from `link.frame.page` (`frames-v1`); without the capability it says "Update the app on your computer". The page is not trusted. `src/ui/frame.ts` has the rules and `tests/frames.test.ts` checks them: the app's own policy comes first in the document (no network), every navigation is refused (`allowsLoad`; `originWhitelist` must stay `["*"]`, because the library hands an address that fails its list to the phone's browser), `FRAME_GUARD` removes WebRTC and sockets in every frame (the policy has no word for them, and a blank child frame has its own), `NESTED_FRAME_GUARD` takes every frame inside a view's page out the moment it is put in (a frame whose address is `javascript:` ran without `FRAME_GUARD`, and packets left: seen on a simulator on 2026-11-20; the relay's frame for a shared space holds the same block word for word), and the page reaches the app only through the messages `readFrameMessage` knows. An answer from a view goes to the message box for the person to send, never straight to the bot; a link asks first. The bridge is the desktop app's `window.botkins`, so a page written there runs here. To check a change by hand, send the demo bot "sandbox": each line says whether one way out was blocked (`BOTKINS_DEV_PROBE` points it at a listener of your own, which shows what really left: HTTP on its port, STUN over UDP one below, TURN over TCP one above).
- **Sections on the Chats screen** (`chat-sections-v1`; the contract is in `docs/link-contract.md`). A section is the person's own way to group their chats: the computer keeps it for them (`link-host/chat-sections.mjs`, in the team beside a member's other marks, for the owner too), nobody else sees it, and the app's workspace knows nothing of it. The part `chatSections` and `ChatSummary.sectionId` are the caller's own. `ChatList.tsx` is the screen and its scroll frame; `ChatBoard.tsx` the list with the hold-and-move drag (Home's rule and numbers, `DRAG` in `src/features/home/drag.ts`): onto a section, onto a day's group to take the chat out, onto Pinned to pin it. `sections.ts` has the plain logic (the order of the list, the group a dragged chat is over, what a drop asks), `sectionMenus.ts` the menus in the words bot sections on Home use. `tests/chat-sections.test.ts` covers the rules, the list, the drag's logic, and an owner and a member on the demo. A new `link.…` call also needs its line in `desktop/desktop/terminal/coverage.mjs` (the desktop's test fails without it).
- **Selecting part of a message.** A double tap, or "Select text" in a message's menu, turns that message into one native text view that can't be edited (`SelectableText`), so the phone's own handles and menu (Copy, Look Up, Share) work on it. `selectable.ts` turns the Markdown into plain runs, so what is copied has no Markdown marks. The double tap is a native gesture (`useTapGesture` with two taps): two quick presses on a view do not both arrive. Such a text view never says it lost its selection, so `selecting.ts` ends it: a short tap elsewhere in the chat, a touch on the message box, or the chat closing.
- **Holding a link in a message.** A hold on a link (a Markdown link, a bare URL, an email address) opens that link's menu (Open link for web links, Copy link, Share…) and not the message's. The message's menu is one native menu (`TextHoldMenu` in `src/ui/LinkHold.tsx`, a `HoldMenu`) that can't be kept shut, so a link only says it is under the finger (`onPressIn`) and the same menu opens with that link's items; the items and their ids are in `linkMenu.ts` (tested by `tests/link-menu.test.ts`). The comment at the top of `LinkHold.tsx` has why Android needs the items kept until the menu closes. A tap still opens a web link; a press held as long as a hold does not.
- **Back to the newest message.** `ScrollToLatest` floats over the chat when the newest message is out of view. A manual scroll into history keeps the reader's place. “Show beginning of completed response” positions a finished reply once. A new turn resumes following if the app made the jump. Sending or tapping Scroll to latest also resumes following.
- **The context window.** A chat that has a measurement (`ChatSummary.context`) shows `ContextMeter` in its header: a ring and a percent, tinted by how full it is. A tap opens `ContextSheet` (route `/chat/context`): the parts of the window, the replies' tokens, what is loaded for the chat, and Compact. The sums are in `contextMath.ts`.
- **What a provider says about a model.** `ModelInfo` in `src/link/types.ts` has optional facts (context window, output limit, vision, tools, thinking-level notes and more) that need `models-v2`. Each is absent when the provider does not know it. Show a fact only when it is there, and never show a guess, a zero or a placeholder: `facts.ts` is the one place that decides, and `ModelInfo.tsx` shows it.
- **A turn in order.** `turn.ts` (plain, tested) builds the chat's list: each turn's steps, thinking, text, steers, answers and screen cards by time, the reply last, and one line for a turn that ended without finishing (`endingOf`: "Timed out", "Interrupted", "Needs you", "Stopped", the newest with Try again). The run part (`running[chatId]`) is the turn under way only while its status is "Working" (`underWay`); otherwise it is the newest turn, ended without a reply. Taking an ended turn for one under way was why a chat seemed to lose its history. With `turn-timeline-v1` the computer sends interim messages, answers and times (`docs/turn-timeline.md` is the contract, written for the desktop thread); without it, `src/state/turnMarks.ts` notes where to cut the text while the phone watches the turn. While a chat works, `send` goes with `delivery: "steer"`, as the desktop app's composer does, and a queued message's button says "Steer now" or "Send next" (`live.steerable`).
- **Keeping the work moving.** The computer gives a bot more turns in the same run while its plan has open steps (at most 8, and never past a question, an open request, Stop, a waiting message, a routine or a Proactive run), and when a reply names its next step without doing it (at most 2). It sends `Run.continued`, `Run.plan` and `Run.stoppedOpen`; an older computer sends none, and an older phone ignores them. `keep.ts` (plain, tested by `tests/keep-moving.test.ts`) holds the words, the desktop app's own (`desktop/src/keep.ts`): the quiet "↻ Kept going: N plan steps were open" line, and "Stopped with N open steps" with Continue, which sends "Continue with the open steps." to the chat. `turn.ts` draws the earlier replies of such a run where they came. A question that waited ten minutes arrives as `AgentRequest.detached`: its card says "Waiting for your answer. Your reply starts a new turn.", and the answer starts a new turn that quotes it. The demo computer shows all three with the prompts "keep going", "stopped with open steps" and "waiting question".
- **Helpers.** While a turn has helpers, `HelperRail` ("In the background · 2 running", the desktop app's words) sits above the composer with one chip for each. A tap opens `/chat/helper` (`HelperActivity.tsx`): the helper's state and time, what it was asked, its own steps as they happen and what it came back with. The plain logic is in `helpers.ts`. A helper's own steps need `Step.agentId` (`turn-timeline-v1`); without it the sheet says "Update the app on your computer to see this helper's steps."
- **Keep a long chat light (measured 2026-11-20).** Three things made sending slow in long chats, and each has a rule now.
  - **Bytes.** The phone opens every sync in plain JavaScript, at about 1.5 MB a second. A chat's page with whole steps was 600 KB to 1 MB and came again with every message; a running turn's part grew with every step. The phone asks for light steps (`lightSteps` in `src/state/link.ts`, `step-details-v1`), and `StepRow` reads a step's input and output with `link.step` when it is opened. Before you add a field to a message, a run or a step, ask how big it gets in a turn of 300 steps.
  - **Row props.** `ChatScreen` renders on every keystroke and on every change from the computer. What it hands to every row (`sendText`, `draftText`, `messageActions`) must be the same object from one render to the next, or every message in view is drawn again. Keep them in `useCallback` and `useMemo`; a new prop for rows follows the same rule.
  - **Row objects.** `reuseItems` (`turn.ts`) keeps a row that didn't change as the same object. A work row reads only its run's id, so it is kept when the run arrives again. Keep ordinary streaming appends local to the active row. Group the history again only when the shape or order of the timeline changes.
- **A send whose answer was lost.** The computer can take a message while the answer is lost on the way back. `arrived` (`compose.ts`) then finds the message in the chat or waiting its turn, and the draft is not put back, or is taken out again when the message shows up a moment later.
- **The activity sheet** (`RunActivity.tsx`, route `/chat/activity`) lists a turn with tasks first, then subagents and background processes, then newest-first tool calls, thinking, updates and teamwork. Each shows only when there is any.
- **Chat display.** Settings › Chat has independent choices for Steps and Thinking and updates. Folded keeps that activity in the working rail. Open also shows it in the conversation. Steps offers Failed only, which shows failed calls in the conversation and keeps every call in the rail. Thinking and updates offers Hidden, which hides notes and reasoning in the conversation and the normal rail view. Fold finished steps controls completion separately. On, it puts the turn's work under one expandable line with the elapsed time and total step count. Off, it keeps the visible work in order. The person's messages, steers and answers and each bot's final reply stay in the conversation. A fresh install defaults to folded activity. A previously explicit Every step choice keeps its open transcript after completion.
- **The work, drawn as T3 Code draws it** (the owner's pick, 2026-11-22). No card, box or line around the bot's work: the newest part of a turn under way is led by the bot's face, still, with what it is doing in ink and its latest thought muted beside it ("Coding · One promise per session…", `LiveTurn.tsx`), and its steps sit under that as quiet rows, each with an icon for its kind (`WorkRows.tsx`, the kind is `stepKind` in `turn.ts`). **The live line shimmers** (T3 Code's live row, the owner's pick 2026-11-23): while the bot is on its turn and nothing waits for the person, the running step, or the lead's "Coding" while no step runs, is muted with a soft band of ink sweeping across it (`Shimmer` in `src/ui/Shimmer.tsx`, timing in `src/ui/shimmerSteps.ts`, tested by `tests/shimmer-steps.test.ts`; the computer's is `desktop/src/Shimmer.tsx`). One line at a time. It keeps the battery rule: a native `Animated` value stepped on timers (12 steps a sweep, then a rest with no updates; about four native updates a second and no React render), drawn only while the screen is in view, the app is in front and the person has not asked for less motion, which draws the line in ink, still. Nothing else spins or shimmers; the status capsule stays still, as T3 Code's does. The band's mask is `@react-native-masked-view/masked-view`, already in the native build through expo-router. **Thinking and interim texts are drawn apart** (`Aside.tsx`): an interim text is something the bot said, so it reads like the reply (full size, a shade quieter, no label or box), and thinking is the bot's face with a muted line. Open shows both in full. The activity sheet shows reasoning and updates in Folded and Open. The reply is never folded or hidden. The bot's work keeps 48 points from the trailing edge and is at most 600 points wide (`workWidth` in `bits.tsx`); the reply's text, tables and code keep the full width.
- **The status capsule** (`StatusCapsule.tsx`). While a turn runs, a glass capsule floats over the message box: the bot's face (the speaker in a group chat), what it is doing, how long it has been at it and its step count ("Coding | 0:42 · 3 steps"). A tap opens the activity. The Todos rail on its right opens the session’s task list. Finished lists stay visible through their turn and clear when the next turn starts. Lists with pending, in-progress or blocked tasks carry forward. Its clock ticks once a second only while the chat is on screen and the app is in front.
- **The open chat** (T3 Code's look, 2026-11-22). The chat fills the screen and what floats over it is measured, so the rows rest clear of it and scroll under it: on a phone with Liquid Glass the bar is see-through (`hasGlass`), with the page's color solid under it and a short soft edge below (`Fade` in `ChatScreen.tsx`); the banners sit under the bar; the message box floats on glass at the bottom, behind the same fade. Beside the Chats list the pane's own bar floats the same way. The list is inverted, so iOS 26's own scroll edge effect would blur the whole chat under a see-through bar: `EdgeFree` turns it off for the list with `ScrollViewMarker` (from `react-native-screens/experimental`), and the list doesn't let the system add the bar's height (`contentInsetAdjustmentBehavior="never"`). Without Liquid Glass the bar is the page's color, as before.

- **Connect cards.** A bot that needs a Composio app calls `request_app_connection`, and the turn gets `run.connects` (the computer's `desktop/connects.mjs`). `ConnectCard.tsx` draws each one with the desktop's words, with rich cards off too. Connect is `composio.cardOpen` (the computer's own Composio account, so its owner only; a member reads "Waiting for the computer's owner"): it answers the page to open, which is never saved or shown in the chat. Coming back to the app calls `composio.cardCheck`, and the computer goes on with the chat once the app is connected.
- **MCP Apps.** A tool of an MCP server that declares an interactive view puts `run.mcpApps` on its turn (the computer's `desktop/mcp-apps.mjs` runs that server itself and keeps the view, the tool's input and its result). `McpAppCard.tsx` draws the view in a web view, needs `mcp-apps-v1`, and is the saved summary with rich cards off or when the view can't be shown. `mcpApp.ts` (plain, `tests/mcp-app.test.ts`) builds the page (the app's policy first, from the https and wss origins the server declared) and speaks the host's side of MCP Apps; `MCP_APP_BRIDGE` sends what the page posts to its parent to the app, since a web view's page is its own parent. The view's calls are `mcpApps.callTool` and `mcpApps.readResource`, which the computer sends only to the card's own server; a tool that may change something answers `needsApproval`, and the phone asks before calling again with `approved`. Showing the card never runs the tool again.
- **Requests.** `RequestPanel.tsx` docks what a bot asks above the composer; its pieces and plain logic are in `request/` (tested by `tests/requests.test.ts`). Nothing a person must read is cut: choices are full-width rows that wrap, and a "Label — description" choice shows as two lines while the whole string is sent. A choice is picked and then sent with "Send answer", with the desktop app's words (Dismiss, Send answer, Allow once, Allow for this chat). The heading folds the card to one line and says "1 of 3" when more wait. Buttons stack when a label wouldn't fit (`fitsSideBySide`).
- **Secure input.** A request of kind `"secure"` (`secure-input-v1`) asks for one field (single value) or up to eight (multi-value), each `password`, `code`, `secret` or `text` under the label the bot gave it. Each value lives only in its own field's ref, is sent once as `{ action: "accept", content }` (a saved credential as `{ $credential: id }`), and is cleared after sending, on Decline, and when the card goes away. It never goes in the store, a toast, a log, a label or the chat; a failed send says only "That didn't send. Try again." The rules are in the header of `request/SecureInput.tsx`, and `tests/secure-input.test.ts` proves the demo keeps no value. Keeping the value from the bot (a handle in its place) is the computer's half, in the desktop app from 0.15.6; afterwards the chat holds one receipt, the title and the labels that were given.
- **More on requests.** `RequestPanel.tsx` shows what a bot asks of the person: an approval, a question or a form. A command that looks destructive (`looksDangerous`) turns red and needs a press-and-hold on Allow. A question or form field that asks for a secret (`looksSecret`, or a `password` format) is masked and can be answered with a saved credential from `CredentialPicker`.
- **Secrets stay out of state, logs and toasts.** Hold a secret only in the field that is typing it, and clear it the moment the answer is sent. Never write it to the store, `console`, a toast, an error message, storage or a route parameter. To use a saved credential, send the reference `{ $credential: id }` where the value belongs. The phone never receives a credential's value, and no call returns one. A voice provider's key follows the same rule (see "Voice").

## Design rules

The look comes from the Botkins design kit in `design/botkins-kit` (read its README): oat paper, espresso ink, one clay-red action color, and the Botkins characters as the color on the page. The look is modular: a person picks a theme for light and one for dark, a text size and a control size in Settings › Appearance, and every component follows at once.

- **Themes** live in `src/ui/themes.ts` (no React Native imports). "ink" is the default (`DEFAULT_THEME`): black on white by day, white on black at night, written out by hand. A person's own pick replaces it (`themePicked` in `src/state/prefs.ts`). "botkins" is the kit's own tokens. Honey, Fern, Tidepool, Bluebell and Fig are named after the kit's palettes, and Paper is nearly neutral. `makeTheme` builds them in OKLCH, the way T3 Code's themes are: the page, side menu, lines and your bubble all lean toward the theme's hue, dark mode is a night in that hue, and every text color is moved until it reads. Add a theme with one `makeTheme({ id, name, hue, action: { hue, chroma, light, dark } })` line.
- **A theme without color.** Ink sets `mono`, and `useTheme().mono` is true: `IconTile` then draws in ink (only a status color still shows). In Ink the action color is the ink itself, white at night, so never assume white reads on `colors.accent`: use `colors.onAccent` on it, `switchColors(colors, on)` for a `Switch`, and `badgeColors(theme)` for the tab bar's counts (iPhone always draws their number in white). `tests/themes.test.ts` checks every theme's contrast; run `npm test` after you touch colors. A new color key goes into the Botkins tables and `makeTheme`, so every theme has it.
- **Font.** A person picks the font in Settings › Appearance (`src/ui/fonts.ts`, `prefs.font`). The default is the phone's own face ("system": San Francisco on an iPhone, and SF Mono for code), worn until a person picks another (`prefs.fontPicked`; a saved "botkins" without that flag was the old default, not a choice). "botkins" is the kit's pairing (DejaVu Serif Bold for names and headlines, Open Sans for the rest). Every other choice (SF Rounded, Avenir Next, Georgia, Lora, SF Mono) is one face for everything but code. The desktop app has the same default and the same flag. Lora ships with the app (`assets/fonts`, `app.config.ts`); the rest are the phone's own, so a new bundled font needs a native build. Never set `fontFamily` in a screen: use `T` or `useTheme().type`, which carry the chosen font.
- **Text size** (13 to 20, default 16) scales the whole type scale. `T` and the components follow it. Outside `T`, take styles from `useTheme().type` or `useType()`. Do not use the static `typeScale` (the unscaled scale at 16); nothing in `src/features` uses it.

- **Tables** in Markdown fit the width they are given. `tableWidths` in `src/ui/tables.ts` (no React Native imports, tested by `tests/tables.test.ts`) shares the width out by what each column holds and lets text wrap in a cell; a table scrolls sideways only when even the narrowest columns can't sit side by side. `TableBlock` in `src/ui/Markdown.tsx` draws it.
- `src/ui/theme.ts` holds `useTheme()` (`{ dark, colors, type, control }`), `space`, `radius`, `brand`, `tint` and `lift`; `src/state/prefs.ts` holds the choices.
- The root layout (`src/app/_layout.tsx`) calls `Appearance.setColorScheme` with the chosen mode, so the phone's own parts (tab bar, menus, keyboard, alerts) follow it.

1. **Few words.** No paragraphs around components. A label, or one short line, is the most a control gets. An empty screen has a title, at most one line, and one action.
2. **One main action per screen.** It is a `Button` (the theme's action color). Everything else is quieter: `secondary`, `ghost`, a row, or an icon button.
3. **Use the components.** Build with `Page`, `Sheet`, `Group`, `Row`, `IconTile`, `Label`, `Field`, `Button`, `IconButton`, `Chip`, `Segmented`, `Slider`, `ColorPicker`, `Badge`, `Dot`, `EmptyState`, `Loading`, `BotAvatar`, `ProviderIcon`, `AppLogo`, `Markdown`, `Blocks`, `Mascot`. Take colors from `useTheme().colors`, spacing from `space`, corners from `radius`, text from `<T variant>`. No hex colors in screens (bot and brand colors come from `colorOf(bot)` and `brand`), and never assume the Botkins theme: a color that only reads on oat paper fails in Paper or Fig.
4. **Pure simplicity.** Few lines, few boxes. On a long row, put status in the subtitle, not in a trailing `Badge`; keep a trailing `Badge` or `Dot` for one short word. Settings-like screens use `Group`: a quiet card in the surface color with no border. 7. **Touch targets** are at least 44 points at every control size. Every icon-only control has an `accessibilityLabel`. Text follows the person's text size and the phone's on top.
8. **A menu on a hold is `HoldMenu`**, never `MenuView` with `shouldOpenOnLongPress`: a `Tap` inside a `HoldMenu` knows a hold opens the menu and does not also press. `HoldMenu` also puts the menu in a view of its own: while a menu opens and closes, iOS adds a stand-in beside the pressed view, and without that wrapper a row leaving the same list in that moment stopped the app ("Attempt to unmount a view which has a different index"). Lay a `HoldMenu` out with its `style`. A control that floats over content is drawn on `Glass` (Apple's Liquid Glass where the phone has it, a matching blur where it doesn't); the glass only draws, and the press belongs to the `Tap` around it.

Use React Native’s `Animated` with the native driver for anything that loops or repeats because Reanimated commits the whole layout tree every frame unless a flag is enabled that drops presses inside transformed views.

Thinking, planning, browsing, coding, working, retrying, talking and listening loop while on show. Idle, waiting, needs-input, pending and sleeping wait for the next shared wall-clock beat and make one pass per beat, with a small fixed offset for each character. Outcomes and reactions play once. Open eyes blink in short, one-off animations on each character’s own beat. The timing and state rules live in `src/ui/avatarRest.ts`, tested in `tests/avatar-rest.test.ts`. **Where avatars move: the agent you're with moves; lists hold still (the owner's rule, 2026-11-24, copied from OpenBot, which runs its animated avatar only for the agent you are with and a still thumbnail everywhere else; it replaces the rules of 2026-11-21 "Home's primary bot moves" and 2026-11-22 "nothing in a chat pulses").** These move, with the kit's full motion (working loops, idle rest beats and blinks): a bot's own page (`/bot/[id]`, wrapped in `AvatarMotion`), and in its chat the header's face (one bot, or a group's two), the face in the working status capsule while a turn runs, the live voice dock, and the look editor's preview (`LookStage`, part of the bot's own page as on the desktop) (each passes `animated`). The phone's avatar motion setting is on by default, as the desktop's is; a person who turned it off keeps it off. Everything else holds its state's pose, with its badge, and does not loop or blink: Home (its primary bot too), the Chats list, Work, Spaces, Market, pickers, sheets, and every avatar on a message, reply, fold or work row in a chat, and the empty chat. The earlier rule (2026-11-19) still holds inside those screens: only an avatar that can be seen moves. ## The computer's own updates

A phone sees which Botkins its computer runs, checks for a newer release and starts its install (`app-update-v1`; the contract is in `docs/link-contract.md`, agreed 2026-11-20 with the terminal host thread). On a server the phone is the only screen, so this is how Botkins there is kept up to date.

- **Where.** The "Updates" section of the computer's page (`src/features/settings/AppUpdates.tsx`, owner only), in the desktop app's words (its Settings › About): "Check for updates", "Update and restart", "You’re up to date.". When this copy can't install, the computer's own `message` is shown as it comes (pull a new image, `git pull`), with "Open release". "Install updates automatically" shows only where the computer sends `auto`. The plain logic is `updates.ts`.
- **The restart.** Installing asks first (one alert), then Botkins on the computer restarts and the link drops, sometimes before the install's answer arrives (the phone then asks `appUpdateStatus` before it calls it a failure). `src/state/appUpdate.ts` keeps that restart in memory, per computer: for two minutes the link's banner says "Botkins on <name> is restarting to update" instead of "Can't reach" (a tap still tries again), then its usual words. Once the computer answers, a toast says how it ended from `last` (a rollback too), and the page's "Last update" row keeps saying it, with the computer's own note after "Updated from …" when an install that worked has one (`message` with `ok: true`); a `last` is this install's when it differs from the one shown before it, so the two clocks are never compared. After 12 minutes without an answer the phone says so. `restartStep` and `afterRestart` in `updates.ts` decide all of this.
- **One computer at a time.** `Desktop.tsx` keys the section by the computer, so after a switch nothing of the last computer's update shows.
- **Directly and through the relay.** Unlike the screen grant, the calls work through the relay: a server is usually reached that way.
- **The calls** `appUpdateStatus`, `checkAppUpdate`, `installAppUpdate` and `setAppUpdateAuto` take no version, address or channel; `link-host/methods.mjs` cuts the first three to nothing and the last to exactly one boolean, and `team.mjs` keeps all four for the owner.
- **The notification.** The computer's app calls `link.push.updateAvailable(version)` when it learns of a newer release: each owner device is told once per version (counted only once the relay took the alert, so a failed send is tried again at the next check), sealed, under the computer's name, unless "A Botkins update is out" is off in Settings › Notifications (`updates`, on by default; a phone registered before counts as on). A tap opens the computer's page.
- **To try it**, start the demo computer with `BOTKINS_DEV_UPDATE` (see the table).

## Plugins

Plugins add skills, tools (MCP servers), hooks, agents and commands to bots (`plugins-v1`; the contract with the desktop app is `docs/plugins.md`, agreed 2026-11-19, desktop 0.15.7). They are the GitHub Copilot format, so GitHub's catalogs (`github/awesome-copilot`, GitHub's default, and `github/copilot-plugins`, which Botkins adds), Hindsight-style memory plugins and a person's own folders all work. Built 2026-11-19.

- **The computer does the work.** It reads the catalogs (the phone never fetches GitHub), installs into its own data folder, turns a plugin on for all bots or chosen ones, and runs its hooks through the SDK with its settings in their environment only.
- **Ids are opaque.** Show `name` and `marketplace`; never parse an id.
- **Reviewed bytes.** Install and update send the `revision` of the preview the person saw. When one is refused, read the preview again and show it. A plugin that runs commands on the computer (a hook or a local tool) asks first before install, update or turning on.
- **Warn, never block** (the owner, 2026-11-21): "warning a user as they enable a plugin is fine, but blocking them is not unless it truly looks malicious with a high confidence (supply chain, prompt injection or credential stealing for example)." An alert with "Turn on anyway" is fine; a refusal, a hidden button, or switching something off by itself is not. The one block the computer keeps is a copy whose files are not the reviewed ones. This holds for the computer's app too: route a block there to its thread. A switch-on and a choice of bots send the installed plugin's `revision` as it was on the screen.
- **What a plugin starts is shown whole** (`plugin-starts-v1`, built 2026-11-21 after a fault in the app: a plugin could show "runs nothing" and run code; `docs/plugins.md` has the contract and the phone's final words). A description that carries the computer's mark (`starts: 1`) says everything the plugin starts. **Decide about one description from its own mark** (`showsAll` in `logic.ts`): with it, ask when something runs; without it, ask first always (`consent`). The capability is only for the sentence about an older app (`useOlderComputer`). Show a tool's whole line, folder and environment, a hook's whole command, headers with their values, where each setting goes, what is not run and the other files (`toolFacts`, `hookFacts`, `sentToLines`, `notRunRows`, `otherFilesRows`; drawn in `parts.tsx`). A long text may fold only behind "Show all N characters": never cut one without saying so.
- **Text shown for a decision goes through `shownText`** (`src/ui/shownText.ts`; the computer's rule, held by `tests/shown-text.test.ts`): a command, an argument, a folder, an address, a header, an environment value, a name beside a question, an approval's command. Each control and format character is written as its number. Never use it for a chat's or a bot's name: a joiner and a variation selector are correct writing there.
- **A plugin the computer switched off** (`enabled: false` with a `detail`, not in error) reads "Off · Needs review". Only a computer up to 0.17.2 does that (`switchedOff`); a newer one switches nothing off, and its reason is the first of the plugin's `warnings`. Its page shows the computer's sentence, then what it runs, then "Turn on"; with `repair: "update"` the button is Update. Two notices are shown one time each and remembered on the phone (`prefs.toldNotices`, `reviewNotice` and `skillsNotices`): over Marketplace › Plugins, and in Settings › Skills for a plugin that has skills. Never tell these cases apart by the words of `detail`.
- **Folder plugins** are a copy of the folder taken when it was added (the folder itself can change). One arrives on (an older computer added it off), and "Update from folder" takes a fresh, reviewed copy.
- **Secrets.** A secret setting is typed only in its field and sent once with `plugins.install` or `plugins.configure`, then shows only "Set". A saved credential is sent as `{ $credential: id }`, accepted only in those two places (`link-host/methods.mjs`, `credentials.mjs`), and `parts.mjs` drops any secret field's `value`.
- **Sign-in.** An OAuth tool with `serverId` signs in with `signInMcpServer(serverId)`.
- **Other harnesses** (direct Claude, Codex, OpenCode, ACP) load only a plugin's skills; the page shows the computer's `limits` sentence.
- **Refresh.** A pull down on each Marketplace view, and the computer's refresh button beside its Marketplace tabs, read the catalogs again (`refreshCatalogs` in `calls.ts`; `plugins.refresh` with `market-refresh-v1`, otherwise only the marketplaces), then the skills and the list on screen. The list shown stays; only a failure is said, as a toast.
- **Where.** `src/features/market/plugins/`: `calls.ts` (every wire name), `logic.ts` (plain, tested), `Plugins.tsx` (the list), `PluginPage.tsx` (a plugin, installed or not), `InstallSheet.tsx`, `UpdateSheet.tsx`, `AddMarketplace.tsx`. The folder sheet takes `use=plugin`.
- **To try it**, use the demo: keepsake-memory (settings, headers and hooks), tracker (sign-in, a stream), sqlite-explorer (a local tool with arguments, a folder, an environment and other files), notify-me (a hook that is not run), legacy-formatter (an error), writing-skills (an update), `/Users/demo/team-skills` from "Add from your computer", and `Code/review-kit` from Skills › "Add from folder…" (a plugin folder, installed as a plugin). `BOTKINS_DEV_PLUGINS=held` starts with plugins that have a note from the computer's update (still on) and one that needs an update as its repair; `old` plays a computer from before the mark.

- **Install makes nothing.** It opens New bot (`/bot/new?template=<id>`) filled in; the person changes what they like, the look too, and Create makes the bot with `addBot`. A template from a marketplace that isn't built in says "Someone else wrote these instructions: read them first."

On the computer: Settings › Marketplace › Agents (`MarketAgents.tsx`), and the Marketplace button left of New chat; `botkins templates browse`, `show` and `use` in a terminal.

They live in `link-host/starters.mjs`, a copy of the computer's `desktop/starters.mjs` (its `test/starters.test.mjs` fails when the two differ). Home's first run lists them when there are no agents to bring in, and each opens New bot filled in (`/bot/new?starter=<id>`); New bot's "Start from template" shows them first. Create sends `starter`, and the computer keeps `starter` and, for Chief of Staff and Money manager, `suggestProactive` on the bot for the Proactive setup to read.

## Artifacts

What a bot made or was given: files it wrote, pictures, video and sound it sent, uploads, exports (`artifacts-v1`; built 2026-11-19). The computer keeps the index; the phone never looks at the computer's disk.

- **The four calls** (`Calls` in `src/link/types.ts`; their shapes are checked in `link-host/methods.mjs`): `artifacts.list` (a bot's artifacts, 50 a page, newest first; `kind` "files" or "media"; `folder` lists what is in a folder artifact), `artifacts.read` (a file in pieces of at most 512 KiB), `artifacts.thumbnail`, and `artifacts.resolve` (the artifacts behind paths written in a chat, 20 at a time). `revs.artifacts` goes up when the index changes.
- **Where.** A bot's page has an "Artifacts" section (the newest 3 and "All artifacts"). The list page (`/artifacts`) has the chips All · Files · Media (Media is images, video and audio; Files is everything else, folders too). The preview (`/artifacts/view`) is chosen by type (`previewKind`): picture, video and sound, text, Markdown, code, PDF, and a fallback with Share. Its bar has Share, Save to Photos (pictures and video) and Open chat. Everything is in `src/features/artifacts/`: `logic.ts` (plain, tested), `data.ts` (lists, downloads into the phone's cache in pieces, thumbnails, path lookups; emptied on a change of computer), and the screens.
- **Paths in a chat.** `src/features/chat/paths.ts` finds the absolute paths and `MEDIA:` attachments in a message. A path becomes a link only after the computer says it can show it; anything else stays plain text. The rules and 40 cases are shared with the desktop app in `docs/path-detection.json`: change the cases there first, then both detectors. `Markdown` takes the links through its `paths` prop.
- **Media in a reply.** A `MEDIA:` attachment the computer knows is drawn in the reply where its line is, and the raw line is not shown (`messageParts` in `logic.ts`, `InlineMedia` in `ArtifactBits.tsx`): a picture as itself, anything else as a chip that opens it. One the computer does not know stays as the text it is. A picture comes from the computer's small picture first; the file itself is read when it is at most 3 MB (a sharp picture), or at most 8 MB when the computer makes no small picture (a server host has no display to make one with). The computer takes a `MEDIA:` file only from the bot's own folder, a project folder or the chat's session folder: a path in prose never opens another place on the computer.
- **To try it**, send the demo bot "what did you make": its reply has paths that resolve, one that does not, a whole-line path in a code block and an attachment. "mockups" sends three pictures, each under a line of its own, and one the computer does not know.

## Teams: people in a chat, and each person's own view

A team's members share the owner's computer under a role. `team-people-v1` (built 2026-11-20; the rules are in `docs/link-contract.md` and `link-host/team.mjs`) makes three things each person's own.

- **A chat is its people's.** Its starter and those invited see it and hear of its replies; nobody else is notified, the owner included. "Invite" in a chat's menu opens `/chat/people` ("People in this chat", `src/features/chat/ChatPeople.tsx`): one row per person with a switch and "Started this chat", "Invited" or "Not in this chat" under the name ("You" for the person looking); the starter and the owner switch people in and out, someone invited sees the switches locked and has "Leave chat". The words are the desktop app's. Someone invited takes part but does not rename, compact or delete the chat or change its model, so the menu leaves those out. The plain logic is `people.ts`.
- **A view is its person's.** A member's hidden and pinned bots, their order, and a chat's pinned, archived and unread marks are kept for them by the computer. `useCanArrange()` (`@/state/hooks`) says whether the person may pin, hide and order bots: a member needs only to see them. Sections and "Make primary" are the owner's arrangement and are not offered to a member.
- **What a member receives** is cut on the computer (`filterParts`). A new part has to be cut for members there, with a test: it starts from every part.
- **Admin mode** (the owner's decision, 2026-11-20) is what an owner device is shown, never what the owner may do. Off at first and kept for each owner device: the phone is sent the chats the owner started or was invited to, the spaces the owner made or was given, and no bot a member made; a bot's approval request still arrives, with its chat listed while it waits. On: everything, as before. The switch is in Settings › Team ("Admin mode", shown when `meta.you.admin` is a boolean); Home shows the tag "Admin mode" beside the computer's name while it is on. The cut is `ownerParts` in `link-host/team.mjs`; `tests/admin-mode.test.ts` holds both modes.
- Not built: projects, tasks and artifacts for members.
- `tests/team-people.test.ts` holds the rules and runs an owner and two members against the demo. To try it by hand, start the demo with `BOTKINS_DEV_AUTO_APPROVE=1` and join a second person with its invite code.

## Spaces

A **space** is a named page of panels on a host: private, or shared with members its maker picks, with all members, or with anyone who has a link (`spaces-v1`; the contract is `docs/spaces.md`, which this thread owns; approved mockups are in `design/mockups/spaces.html` of the working folder). Today, Feed, Ideas and Goals each become a space. Built so far (2026-11-20): the link host's half and the demo computer. The relay's routes and page, publishing a link's copy, notifications and the phone's screens are still to come; until they are, the phone shows today's Today page.

- **Content is the app's; who may open it and each person's view are the link's.** `spaceCan` and `spaceView` in `link-host/team.mjs` are the rules (pure, tested): the maker and the owner own a space, a grant or "all members" opens it, and for anyone else it does not exist. A member's role applies on top (`spaceRule`; the scope key stays `today`). `link-host/spaces.mjs` keeps sharing, each person's order, pins, last-opened mark and "Notify me" in the team, and who is looking now in memory.
- **What each device is sent.** The app's own list is never sent. Every person, the owner too, gets their view of it as the `spaces` part (`SpaceSummary[]`); a space's content is read with `spaces.read`, again when its `rev` passes the one held. `panels` and `board` stay for an app that doesn't know spaces.
- **A custom view on a panel** is found by the panel's blocks (`panelOfFrame`), then its space, then `spaceCan`. Never search a part's JSON for an id: people write into panels (state, notes).
- **A new call** needs its shape in `methods.mjs` (`spaceArgs`), its row in `TEAM_METHODS`, and its space check in `spaceRule`. `tests/spaces.test.ts` fails when a name from either table of the contract has no team policy.
- **Share by link.** The computer puts a sealed copy of the space on the relay and takes it back (`link-host/space-links.mjs`: when it is first shared, 20 seconds at the earliest after a change, once a day; a copy that should no longer be out stays in `team.spaceCopies` until the relay says it is gone, tried again at growing gaps and at every start). The relay cannot read a copy: the key is only in the link's fragment. The relay's half is in `relay/` (`src/shared.ts` the checks, `src/space.ts` the page and the frame, `src/space-page.js.txt` and `src/space-frame.js.txt` their scripts; `relay/README.md`, "Spaces shared by link"). The page draws what a copy says as text only, and a panel's own page in a frame with no origin and no network. The frame's policy, what it removes and the page's colors are the phone's own (`src/ui/frame.ts`, `src/ui/themes.ts`): `tests/space-page.test.ts` fails when they drift. A summary's `linkState` says "leaving" (a copy is still being taken back) or "off" (the relay is off). `tests/space-links.test.ts` runs the computer's half against an in-memory relay that decides with the real relay's checks.
- **The phone's screens** are in `src/features/spaces/`: `Spaces.tsx` (the Spaces tab: On Home, More and, for the owner with Admin mode on, From members; then Panels on Home), `HomePins.tsx` (Home's Pinned section, where Today sat: each pinned space as a card that says what its first three panels say, then each pinned panel as a card), `PanelTile.tsx` (a panel as a card: its title and the one thing it says, which is the panel widget's `panelHeadline`; a hold has Pin to Home), `SpacePage.tsx` and `SpaceView.tsx` (a space: its panels as cards, or open with small panels two up and an app right in its card; cards for Feed, Ideas and Goals; the bar pins it to Home, shares and has the menu; the glass bar asks about it and the plus adds a panel), `PanelPage.tsx` (a panel, opened, with its notes; its bar pins it to Home), `icons.ts` (a space's icon), `ShareSheet.tsx`, `NewPanel.tsx` and `AskSheet.tsx`. `logic.ts` has the words and the order (tested by `tests/spaces-phone.test.ts`), `data.ts` the reads: a space's content is asked for with `spaces.read` and asked again when its `rev` in the list passes the one held. A computer without `spaces-v1` keeps today's Today page.
- **Cards or open** (the owner's mockups, 2026-11-22). A space's panels show as cards until the person sets that space to **Open** (the switch on its page; `prefs.openSpaces`, `useSpaceOpen` in `data.ts`). A card runs nothing: no web view is made for an app panel until the space is open or the panel is opened. Home shows only cards. Never show a panel running on Home.
- **Pins on Home.** A pinned space is the computer's (`link.spaces.arrange`, as before). A pinned panel is this phone's own (`prefs.homePanels`, `setPanelPinned` in `data.ts`; the plain logic is `withPanelPin` and `panelPinsHere` in `logic.ts`): it is not sent to the computer, so another phone does not have it. A pin of another paired computer is kept and not shown, and a panel that is gone takes its pin with it. The words are "Pin to Home" and "Take off Home", for a space and for a panel.
- **An app panel's saved state.** `botkins.state` in the phone's view bridge (`src/ui/frame.ts`): `get` is answered from the panel's `state`, `set` goes to `spaces.patchState` only within three seconds of a touch in that view and once a second at most (`HtmlFrame.tsx`; the page can't forge a touch, since the app sees it before the web view does), and a change from elsewhere is told to the page (`stateRev`). Outside a panel `get` is `{}` and `set` is `false`.
- **A panel's asks and project.** A panel can carry `asks`: up to 3 things its bot says are worth asking next. `PanelPage.tsx` draws them as glass chips over the ask field (`asksOf` in `logic.ts` is the one place that reads them). A tap opens the ask sheet with the chip's words in the field and sends nothing; the route names only which chip (`ask`), never the words. A panel without `asks` has no chips: never make any up. The owner's New panel has a **Project** row (`panelProject`): it starts on the space's own project, and `spaces.newPanel` takes `projectId` from the owner only. A project's page lists its panels from the owner-only part `projectPanels` (every panel with a project, in any space); `panels` holds only the Todays'.
- **A person's own change is not news to them:** no dot (`changedSince`), no count in the line, and no count in the list (`by` on a space's items, `spaceView` in `link-host/team.mjs`).
- **Putting spaces in order.** Hold a space, then move: in the Spaces tab (`Spaces.tsx`) it reorders among On Home or More, and a drop under the other heading pins it to Home or takes it off. Home's cards follow that order and take no drag. What members made ("From members") neither moves nor takes a drop. `sortable.tsx` is the drag (Settings › Appearance › Tabs uses it too; its side-by-side mode, `across`, has no caller since Home's row of chips went), with Home's rule, numbers and slot math (`DRAG`, `pickSlot`, `shiftOf` and `restingTop` in `src/features/home/drag.ts`). `spaceItems`, `spaceDropPlan` and `applyArrangement` in `logic.ts` say what the list is, what a drop asks of the computer (`link.spaces.arrange`) and what is shown until its answer arrives (`useArranging` in `data.ts`). A still hold opens the menu, which has Pin to Home, Move up and Move down, as VoiceOver's actions do.
- **Alerts about spaces** (`space-alerts-v1`, named by the link while the app has spaces; built 2026-11-21). `link-host/space-alerts.mjs` picks who is told and writes the words: a note goes right away to everyone who can open the space and has not set "Notify me" to Off; a change goes to those who chose "Every change", at most once in ten minutes for each space and person; once a day, from 8:00 until noon in the computer's time zone, each person is told what changed since they last looked. Nobody is told of their own change, of a space they are looking at, or of a space their device is not shown. The app says what happened with `link.spaceEvent(…)` (host-side; the demo does it through `backend.onSpaceEvent`, wired in `dev-host.mjs`). The alert is sealed, kind `"space"`, with the space (`s`) and the panel (`p`): the notification extension passes them on (`targets/notify`), and a tap opens there (`spaceRoute` in `logic.ts`, used by `openFrom` in `src/state/push.ts`). Settings › Notifications has the phone's own **Spaces** switch (`PushPrefs.spaces`). `tests/space-alerts.test.ts` runs it with an owner and two members.
- **The widget of a panel** (built 2026-11-21; `docs/spaces.md`, "The widget of a panel"). `targets/widgets/PanelWidget.swift` is the widget (`BotkinsPanel`: Lock Screen and Home Screen). It reads `panels` in the widgets' snapshot: `panelHeadline` and `panelParts` in `src/state/widgetData.ts` say the one thing a panel shows and which panels there are (tested in `tests/widgets.test.ts`), and `src/state/widgets.ts` writes them, reading the pinned spaces when such a widget is on show. A tap opens `botkins://open/panel` (`src/features/open/OpenPanel.tsx`). Never make up a number for a panel: a panel that says nothing shows its title alone. To look at its views without a build, compile the target's Swift with a small harness and render them (`previewFamily`, `previewPanel`), as for the cards.
- **To try it**, the demo has the owner's four built-in spaces, "Launch" (shared with all members, with a checklist app that keeps state and a note) and "Money" (private, attached to a project). `BOTKINS_DEV_SPACES=off` leaves the capability out. The demo makes links without a relay; nothing is published.

## Several computers

A phone can be paired with up to 8 computers (`MAX_COMPUTERS`). It follows one at a time, "the computer in use"; the others stay paired. Built 2026-11-19.

- **The list.** `src/state/computers.ts` has the plain logic (add, switch, unpair, read what was saved), and `src/state/link.ts` keeps the list: `pairWith` adds a computer and uses it, `switchComputer(serverId)` uses another, `unpair()` removes the one in use and goes on with another when there is one. The store has `pairing` (the one in use) and `pairings` (all of them).
- **Saved** in the keychain through `keep.ts`: an index (`botkins.computers.v1`: the ids and the one in use) and one entry for each pairing (`pairingKey`), because a keychain value is small. The single pairing an older version saved (`botkins.pairing.v1`) becomes a list of one the first time it is read.
- **A switch starts over** (`startOver`): the link to the last computer is closed and the store is emptied. A cache that belongs to one computer and lives outside the store (the wiki, plans and limits, password managers) registers with `onComputerChange` in `src/state/store.ts` so it is emptied too. Add yours there, or it shows the last computer's data.
- **The two switchers.** A hold on the computer's name at the top left of Home opens a menu of the computers with "Connect a computer…" (`computerActions`; `src/features/home/computers.ts` acts on it). Settings › Computers and teams (`/settings/computers`, `src/features/settings/Computers.tsx`; also a row on the computer's page) lists every computer and team, the one in use ticked; a tap on another switches. Under them: "Connect a computer", "Join a team" and "Set up a new Botkins". "Unpair from <name>" is on the computer's page (Settings, or a tap on that name) and removes only the computer in use.
- **The first screen and Set up.** Welcome (`src/features/pair/Welcome.tsx`) has three cards: "Connect to my computer" (the scanner, which has "Enter a code instead"), "Join a team" and "Set up a new Botkins". That last one is the `/setup` sheet (`Setup.tsx`): the download page for a computer (open, share or copy the link) and "Deploy to Azure" (`setupLinks.ts`, checked by `tests/setup-links.test.ts`), then "Connect to my computer".
- **Notifications come from every paired computer.** The phone registers with a computer when it uses it. The notification extension has a key for each paired computer (`setPushKeys`, entries "key:<id>"), tries each on a sealed alert, and notes which computer's key opened it (`host`); a tap on such an alert switches to that computer first (`openFrom` in `src/state/push.ts`). Turning notifications off tells the computer in use and, over a short link of their own, the others (`tellOthers`); one that can't be reached then is told the next time it is used.
- **Still one computer at a time:** a bot's question to the phone (device access) and a Live Activity started from afar are answered and shown only for the computer in use. A Live Activity's state names no computer.

## The screen's level on a headless host

A server with no window (a Linux box, a container) has no Settings › Phone, so nobody could turn the screen on there. On such a host the phone sets the level: Off, View only, or View and control (`screen-grant-v1`; the rules are in `docs/link-contract.md` and the header of `link-host/grant.mjs`). Built 2026-11-19.

- **Where.** The "Screen" section of the computer's page (`src/features/remote/ScreenAccess.tsx`). On a computer with its own settings it shows the level and "Change this on your computer". On a headless host it shows the three levels with what each grants, whether a display is running, and who set the level.
- **The gate.** Turning a level on asks first what it grants (an alert), then iOS asks for Face ID, Touch ID or the passcode, because the phone signs the computer's ticket with its presence key (`modules/botkins-presence`, wrapped by `src/state/presence.ts`). The key is made just before pairing (`pairWith`) and its name on the phone is kept in the pairing (`presenceTag`). A phone with no passcode, an older pairing, or a pairing made through the relay has no key: the section says to pair again. Turning the screen off is one tap, with no question.
- **Only directly.** The computer refuses these calls through the relay. The section says so when the phone is away.
- **Nothing but a tap starts it.** `grant.ts` holds the only calls and `ScreenAccess.tsx` is its only caller. Do not call `grantScreen` from a route parameter, an effect, a notification, a custom view's message or a phone tool, and do not add a tool or a link handler that reaches it. `tests/screen-grant.test.ts` fails when another file does.
- **The plain logic** (`grantWords.ts`: the levels, their words, why a change is closed) has no React Native imports and is tested there too.
- **To try it**, run the demo computer with `BOTKINS_DEV_HEADLESS=1` and pair with it afresh (an earlier pairing has no key). In a simulator, enroll Face ID first; a simulator has no passcode, so its key is kept under a weaker rule than a phone's.

## The link

The phone and the computer talk over plain HTTP on the local network or a tailnet, and the link encrypts every message itself (X25519, HKDF-SHA256, ChaCha20-Poly1305). `link-host/server.mjs` explains the protocol; `tests/link.test.ts` runs the phone's client against it. The calls a phone may make are listed in `link-host/methods.mjs`; a call that opens a window, a file dialog or the browser on the computer is not in it, except sign-in, which the person finishes on the computer. Where the computer's app opens a dialog, a phone has a call that opens nothing (see "Files and folders without a dialog").

- **Modules.** Beside the protocol, `link-host/` has `credentials.mjs` (the encrypted vault and linked password-manager fields), `managers.mjs` (1Password, Bitwarden and Proton Pass through their command-line tools), `tools.mjs` (runs those tools without a shell), `screen.mjs` and `input.mjs` (frames of the screen, and pointer and keyboard input), `prs.mjs` (pull requests through `gh`), `uploads.mjs` (files from a phone), `push.mjs` (notifications and Live Activities), `device.mjs` (tools that run on a phone) and `voice.mjs` (speech providers). `link-host/README.md` has each one's limits and the trust model. Read it before you change a call; do not copy its numbers here.
- **Skills.** The add menu offers Create skill and, with `skill-upload-v1` and Skills create permission, Upload skill. The file picker sends base64 to the computer in one call. Marketplace › Skills uses `skills-catalog-v1` for search, preview and install. Review the full manifest before installing. The demo supports Markdown, zip and the suggested search “design” offline. The zip reader is a dev dependency for the Node demo host and a runtime dependency on desktop. See `docs/link-contract.md`.

- **Capabilities.** The computer lists what it can do in `meta.capabilities`; the list in `src/link/types.ts` (`Meta`) says what each means. The link adds its own: `sync-push-v1` (one open relay request carries sealed sync updates), `stream-appends-v1` (boolean stream indicators for every chat and reply and thinking text by cursor for watched chats), `step-details-v1` (steps without their long input and output; `link.step` reads one when it is opened), `team-people-v1` (the people in a chat and each member's own view), `member-rename-v1` (the owner renames a member: `link.team.renameMember`), `credentials-v1`, `screen-v1`, `prs-v1`, `uploads-v1`, `relay-v1`, `push-v1`, `device-v1`, `voice-v1`, `devices-v1`, `maintenance-v1`, `screen-grant-v1` on a headless host, and `frames-v1` when the app can hand over a custom view's page. The computer's app names what it supports itself (`backend.capabilities`): `looks-v2`, `routine-delivery-v1`, `routine-no-output-v1`, `models-v2`, `board-mentions-v1`, `provider-usage-v1`, `side-pane-v1`, `files-v1`, `folders-v1`, `artifacts-v1`, `project-artifacts-v1`, `turn-timeline-v1`, `secure-input-v1`, `bot-voice-v1`, `app-update-v1`, `agent-templates-v1`, `market-refresh-v1` (`plugins.refresh`: a pull down on Marketplace reads the catalogs again now), `composio-apps-v1` (Marketplace › Apps for a window that uses this computer from another one; a phone signs in to Composio itself). An older computer lacks some. A screen must check `usePart("meta")?.capabilities` before it shows a feature, and say "Update the app on your computer" when it is missing.
- **Parts and calls.** `credentials` (what is saved or linked, never a value) and `host` (what the person lets phones do: `screen`, and whether the computer uses a relay) are optional parts. So are `phones` (what the computer keeps for each paired phone: its notification choices and which sources bots may use on it, never a token), `asks` (what bots are asking phones for now) and `voice` (speech settings shared by every phone, never a key). The calls are `link.credentials.*`, `link.screen.*`, `link.pullRequests`, `link.upload`, `link.push.*`, `link.device.*` and `link.voice.*`, typed in `Calls`. Call them as `api["link.upload"](…)`.
- **Several devices.** One computer serves many paired devices at once: phones, and other computers' Botkins apps that use this one (`kind` "phone" or "desktop"). Each has its own key; pairing or removing one changes nothing for the others. `link.devices.list`, `.rename` and `.remove` (`devices-v1`) are the registry, shown on the computer's page in Settings (`Devices.tsx`). Each device's `name` is its model; `person` is who it belongs to (`device-person-v1`): "Your name" (`src/features/pair/NameStep.tsx`, route `/pair/name`, opened by `askPersonName()` in every way of pairing and joining) asks for it before anything is sent and fills in the last name given, and the owner changes it with "Change name" (`link.devices.setPerson`; a member's device renames the member). `docs/link-contract.md` is the contract every client builds against, and `src/link/` is the client library the desktop app uses unedited: change the contract first, then both sides, with a test in `tests/devices.test.ts`.
- **The side pane.** A bot can open a pane beside a chat (`side-pane-v1`; the contract is the desktop app's `docs/SIDE_PANE.md`). The link carries it (`pane` on a chat's detail, `panes` on its summary, the call `sidePane`). On the phone it is a sheet over the chat (`src/features/pane/`): it opens when a bot's ask rises (`pane.ask.seq`) and never by itself, closing it tells the computer (`"closed"`), and "Side pane" in the chat's menu opens it when there are tabs. To see it, send the demo bot "open the side pane". A `screen` tab shows a still in the chat as a card (`ScreenCard`, put in the chat's list by `turn.ts` where the bot showed it) and follows the picture live in the pane's tab (`PaneScreen`). The card takes one picture per visible visit. The pane samples at its own size and rate (`screenLive.ts`, tested by `tests/screen-card.test.ts`), only while they can be seen, and never keep the phone awake or send input. Before the owner check has passed they are covered with "Show screen", so a bot never makes Face ID appear by itself; `holdScreen` (`pane/watching.ts`) sends `link.screen.stop` once when nothing shows the screen any more. To see it, send "show me the screen" to a demo computer started with `BOTKINS_DEV_PICTURE`.
- **Routines.** A routine's `deliver` says where its result lands (its own chat, a message in the person's chat with the bot, or a Today item) and `notify: false` keeps it quiet, on the computer and on a phone. Both are on `RoutineInput` and on the schedule entries, need `routine-delivery-v1`, and are in `RoutineEditor.tsx` only when the computer has it. "No output" (`deliver: { to: "none" }`: the routine runs, keeps its history, and publishes no reply and no notification) also needs `routine-no-output-v1`; it is the first choice and a new routine's starting one where the computer has it, and a routine that has it keeps it when edited. The choices and what is saved are in `src/features/work/delivery.ts` (tested in `schedules.test.ts`). The computer marks such a run `noOutput`, and `link-host/push.mjs` sends no "finished" notification for it.
- **At rest in the background.** When the app goes to the background, `LinkClient.rest()` stops following (no waiting request, no probe) until `wake()`; calls still go through. A push that wakes the app in the background follows until one sync has come back (`freshSync` in `src/state/link.ts`) and then rests again (`restIfAway`). A reachable computer costs a phone in the background nothing.
- **Coming back from the background.** iOS closes sockets and drops requests under a suspended app, and the link can't tell until it asks. `LinkClient.wake()` (called when the app comes to the front and when the network changes) marks the path as suspect: it asks the transport to check itself (`options.check`; for the relay, `check` in `src/link/relay.ts` pings every open socket and ends one that stays silent for a few seconds), then the next sync asks for an answer at once with a short deadline. If none comes, the session is dropped and the computer is looked for afresh on every address. Every request goes through `timed` in `src/link/client.ts`, which gives up by itself at its deadline instead of waiting for the transport, because a request the system dropped may never settle and must not hold the link. A new request in the client goes through `timed` too. A stopped client drops its session and probe timer. A late answer can finish a call, but only a new start lets it follow or report changes again.
- **The relay.** Away from the computer's network the phone goes through the relay (`relay/`, a Cloudflare Worker with one Durable Object per computer, deployed at `relay.botkins.app`). The wire format is in `relay/README.md`. A v3 computer keeps two outgoing sockets for one seat. The standby can take over immediately, and the room can hold pending requests for up to 15 seconds if both sockets close. A v2 computer keeps one socket. The computer lists the relay as a single address, `relay!<room>@<host>`; the phone carries the same sealed requests over a socket (`relayFetch` in `src/link/relay.ts`). `findHost` always tries the computer's own addresses first, `LinkClient.route` says which way is in use, and the phone goes back to the direct path when it can. With `sync-push-v1`, a relay follow carries updates at most once per 100 ms, a quiet frame after 25 seconds, and a final answer at four minutes. A polling phone on the relay receives news at most once per 250 ms. Chunks retain their text timing. While following through the relay, the phone first checks for a direct path after a minute. The wait doubles up to five minutes. Waking checks at once and starts the short wait again. The relay sees sizes and timing, never contents. The computer proves its seat with a signature (nothing secret is sent to the relay), and the relay is off until the person turns it on on the computer. Change the wire format in all four places at once: the fake relay, the Worker, `link-host/relay.mjs` and `src/link/relay.ts`. The Worker's push route is a separate, plain forward (see "Notifications").
- **Finding the computer.** Three ways, in this order: the QR code (it carries every address); the computers the phone finds on the network by itself (the desktop app announces `_botkins._tcp` with TXT `v` and `id`; the pairing sheet lists them and the person types only the code); and a typed address with its port, as the way out. A paired computer whose saved addresses stop answering is looked for the same way and matched by `id` (`lookNearby` in `src/state/link.ts`, `LinkClient.learn`). While the app is in front and the computer stays away, it looks again at growing gaps, from 20 seconds to five minutes. It skips the look on cellular or when disconnected. Never make a person type an address when the phone can find it. The demo computer must not sit on the phone's default port (47610) on a machine where the real app runs: a typed address without a port would reach the demo.
- **Trust.** Pairing is a full-trust step: a paired phone can do what the person can do in the app on the computer. Secrets stay on the computer: the phone saves a credential or links a field, then sends `{ $credential: id }`, and the computer fills in the value. Never add a call that returns a secret.
- **The owner check.** Credentials and Screen ask for Face ID, Touch ID or the passcode (`expo-local-authentication`) before they show anything. For Credentials, `checkOwner()` and `useGate()` in `src/features/credentials/shared.tsx` ask once per app session, and `useGate()` also checks the capability. Screen has its own check in `src/features/remote/Remote.tsx`, and asks every time it opens. A phone with no passcode or biometrics passes. Build a new private screen on `useGate()`; do not write a third check. `checkOwner(reason)` takes the words of the phone's question and resolves true when the owner is confirmed, and `useOwnerCheck()` reads where the check stands without starting one (the live screen card uses both).

## Notifications and Live Activities

The computer decides what to tell a phone (`link-host/push.mjs`: a reply finished, a bot needs an answer, a turn is under way) and sends it through the relay's push route, signed with the relay key it already has. The phone's half is `src/state/push.ts` (permission, Apple's address, presence, opening the right chat from a tap, the chat's Live Activity while the app is open) and Settings › Notifications. The phone's choices (`PushPrefs`) live on the computer, in the `phones` part.

- **What is sealed.** An alert's title and text are sealed for one phone and opened by the notification extension (`targets/notify`), so the relay and Apple carry only "New message", "A bot needs you" or "An update is available". Everything that is not sealed: that generic line, the kind of alert, a thread and collapse id that are hashes (Apple sees no chat id), the timing, and the token. If the extension can't open an alert, it is shown as it came.
- **What is not sealed: a Live Activity's plain state.** Apple hands it straight to the Lock Screen: phases, counts, times and the provider. An activity started by a push also carries the chat's or the bot's id, the bot's name and its look in the clear. A chat's card (an older computer's) has a short label that is a step's name only when previews are on.
- **One card for all Botkins** (`activity-all-v1`; `docs/live-cards.md`, section 0, the owner's decisions 2026-11-22). A phone that can draw it registers with `cards: "all"`, and has one card (key `"all"`, `targets/widgets/FeedCard.swift`) with a row for each chat of any Botkin. Only the phone starts it and draws it, in front; the computer draws it the rest of the time (it resends the whole card when the app leaves), and when every chat on it has ended it says so with an alert, then ends it a minute later (`OVER_HOLD_MS`). It also checks its cards when it starts. While it runs, a request's sound comes from the card's update in place of a notification, and a finished turn's notification comes silent when the card's last update made the sound. That sound is the card's own: it plays also when the notification is left out because the chat is open on the computer, and not when the person stopped the turn, finished replies are off, or the app is in front. A step goes at priority 10 every 15 seconds and at 5 between (Apple holds a 5 back on a locked phone), and a row says the step done last rather than "Working…" (`tests/card-push.test.ts`, with a clock the test sets). The view can be looked at without a build: compile `targets/widgets` with a small `main.swift` that renders `FeedLock` with `ImageRenderer`, and run it in a booted simulator with `xcrun simctl spawn`.
- **One card per Botkin** (`activity-bots-v1`; the contract is `docs/live-cards.md`, the owner's decisions 2026-11-20). A phone registers with `cards: "bots"` when the computer names the capability, and then has one card per working Botkin (key `"bot:" + botId`) with up to three chats. The chats' titles, steps, latest sentence of thinking, reply and request travel sealed in `sealed` (AAD `botkins-card-v1`), and the widget extension opens them as it draws (`targets/widgets/Sealed.swift`, the keychain group the push keys are in). `link-host/cards.mjs` holds the rules and is used by both sides: the computer for its pushes (`Push.cards`, `startCard`), the phone for the cards it draws while the app runs (`src/state/cards.ts`, `followCards` in `push.ts`; the native module seals the detail with the computer's push key). With previews off nothing is sealed.
- **Answering away from the app.** A card's and the island's buttons are App Intents (`targets/widgets/_shared/BotkinsIntents.swift`) that run in the app; a notification's actions are caught by `AnswerDelegate` (`modules/botkins-activity/ios/AnswerQueue.swift`, registered as the app launches). Both put the answer in one queue, and `src/state/answers.ts` sends it with `respond` (or `stop`, `retry`). A choice sends on one tap (the owner's rule). A risky approval opens the app (`/open/answer`) and asks for Face ID. A secure input, a form or a long question only opens the app. The notification extension picks the category (`botkins_approve`, `_once`, `_risky`, `botkins_question`, `botkins_open`) from the sealed `q`; `targets/notify-ui` adds a question's choices. The categories are registered in `push.ts` (`setCategories`).
- **Widgets** read a snapshot the app writes to the App Group (`src/state/widgetData.ts` builds it, plain and tested; `src/state/widgets.ts` writes it a moment after a change and when the app goes to the background). One part per paired computer; plans and limits are the computer's `provider-usage-v1` answer, in the app's words (`Snapshot.swift`, `LimitWords`, mirrors `limits.ts`). Nothing in it leaves the phone.
- **Where the key lives.** Both ends derive it from the pairing (`pushKeyOf` in `src/link/client.ts`; `Push.seal` on the computer). The computer keeps no copy. The phone saves it in a keychain group shared with the extension (`BotkinsKeychainGroup`, `modules/botkins-activity`) when notifications are turned on, and removes it when they are turned off. Never write it anywhere else.
- **Tokens.** The computer keeps each phone's notification tokens in `link.json`, and a token Apple no longer takes is dropped. Tokens never go to a phone in a part.
- **A chat's card (Live Activity) is marked done, not ended.** When a turn ends, the card says "Done" (or "Stopped") with how long it took (`finishedAt`), stays, and a new turn in the chat takes the same card over. After 30 minutes without one it is ended (`ACTIVITY_LINGER_MS` on the computer, `LINGER_MS` on the phone). A Botkin's card and the card for all Botkins are ended instead once every chat on them has ended. `src/state/activity.ts` and `activityState` in `link-host/push.mjs` build the same state; `tests/activity.test.ts` holds them together.
- **A card's own address has to reach the computer.** Apple delivers a card's updates to an address of its own, and the computer can change a card while the app is closed only when it has that address. A push can start a card while the app is closed, so: the native module reports the address a card already has (not only changes) and answers `tokens()`; `push.ts` passes every address on again whenever the computer is reached (`tellAddresses`, `syncActivities`); and when a turn ends on a card whose address the computer never got, the computer wakes the app once so it marks its own card done. Every push to one card has a strictly newer `timestamp` than the one before: Apple drops one that is not newer.
- **The computer stays quiet** about the chat the person is looking at: the phone says when it is in front and which chat is on screen (`link.push.presence`), and the app may say when its own window is (`backend.attention`).
- **Background pushes** wake the app for a moment so it can answer a bot's question to the phone (see "Device access"). `src/state/push.ts` defines that task.
- **Some of this exists twice.** The sealed alert's shape (`PUSH_INFO`, `PUSH_AAD` and the JSON) is in `link-host/push.mjs` and `targets/notify/NotificationService.swift`. A card's sealed part is in `link-host/cards.mjs` and `targets/widgets/Sealed.swift`. The answer queue's shape is in `AnswerQueue.swift` and `BotkinsIntents.swift`. A Live Activity's state is built in `activityState` in `link-host/push.mjs` and in `activityStateOf` in `src/state/push.ts`, and its Swift type, `BotkinActivityAttributes.swift`, is the same file twice, in `modules/botkins-activity/ios` and in `targets/widgets`. Apple matches a push to the activity by that type's name. Change both copies together; a phone with an older build must still show something sensible.
- **Check on a real phone.** See "What a simulator can't check" above.

## Device access

Tools that run on the phone: a bot can read the person's calendar, contacts, Health data, location and photos, use Apple Music, add or change some of them, and write a draft email for the person to send. The contract and the tool list are in `link-host/device.mjs`; the phone's side is `src/device/` (the tools), `src/state/device.ts` (answering), `src/state/devicePrefs.ts` (the switches) and Tools › Device access (`src/features/device/`).

- **The switches are the consent.** For each source (Calendar, Contacts, Health, Location, Photos, Apple Music, Mail) the person picks off, read, or read and interact, and the phone asks iOS for what that level needs first. If iOS refuses, the switch stays where it was. The switches are saved on the phone (`devicePrefs.ts`) and sent to the computer (`link.device.sources`). The computer offers its bots a tool only while some phone allows its source at the level it needs. The phone checks again before it acts (`runDeviceTool`), so a stale list on the computer can't reach past a switch. Location has nothing to change and Mail nothing to read, so each offers fewer levels. Music mutations carry a native grant revision and recheck it immediately before playback/library commits.
- **What a tool reads goes only into its answer.** Never into the store, a log, a toast, an error message or the activity list. A tool that fails answers with a sentence written for a bot (`DeviceError`); anything else becomes "couldn't do that just now", because a system error could carry what the tool read. The activity list (`recordActivity`) holds which tool ran for which bot and when, never its arguments or results.
- **Mail only opens a compose sheet.** An iPhone does not let apps read mail. `phone_mail_compose` is marked `hands`: the person finishes it, so it works only while the app is in front.
- **To add a tool**, change all of these, then run `npm test`:
  1. Add it to `DEVICE_TOOLS` in `link-host/device.mjs` (name, source, level, description, JSON Schema `parameters`).
  2. Add it to `PHONE_TOOLS` in `src/device/tools.ts` (the same source and level, its `args`, a plain `label` for the activity list).
  3. Write its runner in the source's file in `src/device/` and put it in that file's tools object, which `src/device/run.ts` spreads into `RUNNERS`. Take arguments with the checks in `args.ts`; shape results with `shape.ts`.
  4. `tests/device.test.ts` keeps the two lists the same: every tool the computer offers must have a runner on the phone at the same source and level, and each takes exactly the arguments the computer's schema lists. A new source also needs its words and permission calls in `src/features/device/sources.ts`, and an entry in `DEVICE_SOURCES` (`link-host/device.mjs`), `SOURCES` (`src/device/tools.ts`) and the `DeviceSource` type.
- **Asks.** A bot's call waits in the `asks` part until the phone it is addressed to answers with `link.device.answer`. A phone that is asleep is woken with a push it doesn't show; if that does not work, the person gets a notification that a bot is waiting. A picture is a file: from the phone it arrives as one of its own uploads, and to the phone it goes through `link.device.file`. A path on the computer is never sent to a phone.

## Voice

Dictation, reading replies aloud and live voice, in `src/features/voice/`. `link-host/voice.mjs` is the one place that talks to speech providers; `link-host/VOICE.md` has every provider's routes and what was and was not checked. Read it, and do not repeat it here.

- **Keys stay on the computer.** A key is typed in `ProviderSheet.tsx` (or a saved credential is picked) and sent once with `link.voice.key`. The settings the phone gets say only `hasKey`. A live session gives the phone at most a short-lived secret for that one session, or no secret at all when the computer talked to the provider itself. A key follows the rules in "Secrets stay out of state, logs and toasts".
- **A voice of a bot's own** (`bot-voice-v1`; the contract is `link-host/VOICE.md`, "A voice of a bot's own"). A bot's page has a Voice row (`BotPage.tsx`) that opens the sheet `/bot/[id]/voice` (`src/features/bots/BotVoice.tsx`): Reading aloud and Live voice, each "Same as Settings" or its own provider, model and voice (and a speed for reading). The choices are `Bot.voice`, saved by the computer with the bot (`updateBot(id, { voice })`, `null` clears); keys stay shared. `botVoice.ts` (plain; `tests/voice-settings.test.ts` keeps it the same as `effectiveTts` and `effectiveLive` in `link-host/voice.mjs`) resolves a bot's voice over the shared one. Reading aloud passes `botId` (`speakText`), and live voice uses the bot's provider (`liveProviderFor`; the computer applies the rest). When a bot's reading provider is "This phone", its system voice and speed are kept on this phone by bot id (`prefs.ts`, `setBotDeviceVoice`), never on the computer. The desktop app has the same card (`desktop/src/BotVoiceCard.tsx`) in the same words. A team member whose role manages bots sees the row and sets the voice of the bots it can see; the computer sends it the shared choices without keys or addresses (`memberVoice`), and a row for a member shows only once they arrive.
- **Settings are the computer's**, shared by every phone (`usePart("voice")`); the phone's own voice and speed for "This phone" are saved on the phone (`prefs.ts`). The features need `voice-v1`: `src/features/voice/state.ts` checks it.
- **The pieces.** `api.ts` is what the rest of the app uses (`useDictation`, `useSpeaker`, `useLiveVoiceReady`, `openLiveVoice`). Dictation uses the phone's own recognizer when the provider is "This phone", and otherwise records and sends the sound to the computer (`link.voice.transcribe`). Reading aloud asks the computer part by part (`link.voice.speak`) and falls back to the phone's own voice. `live/session.ts` owns one live-provider controller. The iPhone hook `useLiveSession.ts` subscribes to it with the normal duplex endpoint, while `features/watch/voice.ts` subscribes with the WatchConnectivity endpoint. Socket providers use the same PCM duplex transport; Codex/WebRTC-only voice uses `live/watch-rtc.ts` and a native custom `RTCAudioDevice` whose microphone and playout belong to Watch. A Watch call does not depend on the iPhone chat screen staying mounted. `VoiceDock.tsx` is still the iPhone UI, with the bot, status, keyboard, Mute, sound strip, Speaker and End. The chat shows what is said because the computer saves the call (`voice-turns-v1`). Each transport reports level, and the existing dock drives a native `Animated.Value` without rendering the React tree for every audio frame. The controller ends when its chat/host/provider changes; a Watch-owned session also ends after Watch reachability is lost. The voice model only talks: its one tool, `ask_bot`, sends the message to the bot's chat, and `live/askBot.ts` waits out the turn.
- **Settings › Voice** is an overview plus one page per feature, like Settings itself. A row shows the provider and one line: what is set, or what is still missing (`settings/summary.ts`, the one place that decides). Each feature page has a row for the chosen provider's key and address that opens `ProviderSheet`; Keys and servers lists them all. The computer's choices are shared by every phone. This phone's own choices (its voice and speed, and how live voice listens: "Live conversation" or "Push to talk", `liveInput` in `prefs.ts`) are saved on the phone, and the page says so.
- **The bot never hears itself.** `live/input.ts` (`MicGate`) decides when the microphone is sent. While the bot's sound plays and for a short tail after, nothing goes (on WebRTC, the track is off from `output_audio_buffer.started` to `.stopped`). The person stops the bot with the Interrupt button, or on the socket paths by talking clearly louder than the echo. Push to talk (`liveInput: "push"`, read when a call starts) sends the microphone only while the dock's sound strip is held: it turns OpenAI's turn detection off (`turn_detection: null`, then commit and `response.create`) and Gemini's (`activityStart` and `activityEnd`). ElevenLabs has no manual turn, so the phone sends silence while the button is up and the agent answers after its own pause. **A turn with no speech sends nothing.** A speech model given silence invents a word ("Qué", then the voice answers in Spanish). In push to talk on OpenAI, a turn whose microphone level never reached `SPEECH_LEVEL` (`input.ts`; `LiveBase.quietTurn` in `types.ts`, from the levels `hears` is given) is cleared on release, like a press shorter than `MIN_TURN_MS`; a call that reports no microphone level is never judged quiet. The person's language from Settings › Voice › Dictation goes to OpenAI as the transcript's `language` hint. A recording sent for dictation or talk by turns is dropped by the phone when it is under `MIN_CLIP_MS` or its metering never reached `CLIP_SPEECH_LEVEL` (`clip.ts`), and the computer refuses a silent or tap-short WAV too (`wavHasSpeech`, `link-host/VOICE.md`). The numbers (400 ms echo tail, 250 ms release tail, the barge-in level, the speech levels) are starting points to tune on a real phone.
- **No provider has been tried with a real key yet.** Everything in `voice.mjs` and in the phone's transports was written from the providers' documentation and tested against fakes. `VOICE.md` lists the places to try first.

| `BOTKINS_DEV_NAME` | The computer's name. The default is `Demo Mac`. |

| `BOTKINS_DEV_APPENDS` | `off` omits `stream-appends-v1` and serves full-string `live` even when a phone asks for appends. |
| `BOTKINS_DEV_TIMELINE` | `off` leaves `turn-timeline-v1` out, as an older computer would: no interim messages, answers or helper steps. |

**What it connects to.** It opens no relay socket unless `BOTKINS_DEV_RELAY` is set. But when a phone paired with it has turned notifications on, it sends them through the relay's push route (`POST /v1/push`), to the relay in `BOTKINS_DEV_RELAY` or else to the default relay (`relay.botkins.app`). So the demo does open an outside connection in that case, and what it sends is sealed or generic (see "Notifications").

It starts with two made-up credentials. To make the demo bot ask for something, send a message that contains:

- `approve`: an approval ("Run a command").
- `which`: a question with two choices and a free answer.
- `sign in`, `password` or `api key`: a form with a username and a secret API key field.
- `long question`: a question with three long choices and a free answer.
- `secure password`: a secure input with one password field. `secure login`: one with a username, a password and an optional one-time code. The demo bot replies with the labels it received, never the values.

To see a turn in order, send `long turn` (about 15 seconds of text, thinking, steps and two helpers; a message sent meanwhile steers it), `ask midway` (a question in the middle, more steps after the answer), `time out` (text and steps, then it ends "Timed out") or `interrupt me` (the same, ending "Interrupted").

To make it open the side pane, send `open the side pane` (and `close the side pane`), or `show me the screen` for a tab with the screen. To make it show a custom view, send `chart` (a bar chart with a button and a link) or `sandbox` (a page that tries every way out of the view and says which were blocked).

Its folder browser shows a made-up home folder and one made-up disk ("Backup"); it never reads a real disk.

To make it use the phone, send a message with `calendar` (or `schedule` or `meeting`), `contact`, `where am I` (or `location`), `photo`, `steps` (or `health` or `sleep`) or `email` (or `mail` followed by a space). The demo bot calls the matching phone tool, which works only when that source is on in Tools › Device access on the paired phone (`PHONE_ASKS` in `link-host/mock-backend.mjs`). One of its chats has a context measurement, so the meter and the sheet have something to show, and a few of its models have made-up details.
