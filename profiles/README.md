# Botkins profiles

Profiles are optional. An installation can pair directly with a host or join a team using the existing Link. A profile adds a shared list of computers, one name and a separately revocable identity for each installation. The account service stores the verified email, display name, optional avatar, passkey public credential, trusted installations and public host descriptors. Each host keeps its own access rules, work and Link keys.

## Enrollment

The app keeps a new random verifier in protected local storage and sends its SHA-256 challenge. It opens the fixed HTTPS profile site with an opaque attempt ID in the fragment. Entering the six digits displayed in the app binds that browser tab to the attempt. A registration or assertion uses a discoverable passkey, user verification, and the exact origin and relying party `profile.botkins.app`. New profiles verify email. Existing profiles also need either approval from an already trusted installation or a code sent to the email originally verified at signup. Only the app holding the verifier can finish. A lost completion response can be retried during the fifteen-minute enrollment window.

The host binds a profile to the principal already authorized by Link. The directory contains host names, pinned public keys and connection addresses. On a new installation, the app requests a single-use proof tied to that host and the new local Link public key. The host redeems the proof and applies the existing local permissions. The service cannot supply a pairing merely by returning a directory entry. Private Link keys stay with individual installations. A trusted installation can delete the profile by confirming its verified email. This clears the account, cloud directory, passkey credential and device authorizations. Each host retains its local workspace. Short-lived email quota reservations contain a recipient digest.

On first launch, choose a profile or keep this device local. A previously configured installation offers to link its existing hosts the first time it runs this version. Each remote host must be reachable and running a version with profile support to approve the migration. A new device can reach a host on its local network or through the relay when the host owner has enabled access away from home.

## Operation

Run `npm ci` and `npm test` in this directory. The tests exercise WebAuthn registration and signed assertions using a software authenticator, a transactional SQLite implementation of D1, and captured email. With the desktop and mobile relay dependencies installed, `npm run test:link` checks migration against two running Link hosts and a connection over a local WebSocket relay and `npm run test:browser` exercises the browser page in Chrome with a virtual passkey. After building the desktop renderer, `npm run test:desktop` drives isolated fresh and upgraded Electron installations through onboarding and host selection. Run `npm run build` to bundle the same-origin browser assets.

Wrangler deploys the dedicated `botkins-profiles` Worker with its `DB` D1 and `EMAIL` bindings. The configured sender is `profiles@login.botkins.app`. Set a random 32-byte or longer Worker secret named `PROFILE_SECRET` for email-code hashing. Apply the schema with `npx wrangler d1 migrations apply botkins-profiles --remote`, then run `npm run deploy`. The Worker serves health at `GET /v1/health`. Existing deployments retain the installed secret.

The service reserves an email send in D1 before contacting the mail provider. It permits 60 sends per rolling 24 hours across the service, five per recipient in that window and one per attempt per minute. Failed sends consume reservations. The Worker allows up to 600 new enrollment attempts per UTC day, rate-limits API traffic by source IP, and caps CPU at 25 ms per request. A profile can store 32 active installations and 256 hosts. Static assets use Workers Assets. There are no cron jobs. Active host access checks revocation on demand. Cloudflare bills the account's aggregate usage, so these limits cannot guarantee a fixed bill when other workloads or public requests consume the available allowance.
